## 一、已修复的 BUG

### BUG-1【严重 · 安全】封禁/删除用户后，旧 token 仍可使用最长 8 小时

**实测复现（修复前）**

```
1. 注册用户 + 登录拿 token     -> 200
2. 封禁前用 token 访问接口      -> 200
3. 管理员执行封禁              -> 200  ✓ 封禁成功
4. 【同一个旧 token】再访问     -> 200  ← 漏洞：封禁完全没生效
5. 该用户重新登录              -> 401  ✓ 只有重新登录才被拦
```

**根因** —— `AuthenticationService.authenticate()` 只查 Redis，不查数据库：

```java
// 修复前
return cacheService.get(TOKEN_PREFIX + token)
        .map(Long::valueOf)
        .orElseThrow(() -> new AuthenticationException("invalid or expired access token"));
```

Redis 里只有 `token → userId` 映射，不含账号状态。于是**"token 有效"被等同于"账号有效"**——但账号可能已被封禁或删除。后果：封禁形同虚设，被封用户最长还能用 8 小时。

**修复** —— token 验证通过后回查一次数据库：

```java
// 修复后
Long userId = cacheService.get(TOKEN_PREFIX + token)
        .map(Long::valueOf)
        .orElseThrow(() -> new AuthenticationException("invalid or expired access token"));
// Token 有效不等于账号有效：账号可能已被封禁或删除。
return userRepository.findById(userId)
        .filter(candidate -> "ACTIVE".equals(candidate.status()))
        .orElseThrow(() -> new AuthenticationException("account is inactive or no longer exists"))
        .id();
```

**验证（修复后）**

```
1. 封禁前旧 token 访问   -> 200
2. 执行封禁              -> 200
3. 【旧 token】再访问     -> 401  ✅ 立即失效
4. 管理员 token 访问      -> 200  ✅ 未误伤
```

> **面试点**：这是"认证"与"授权状态"分离的经典陷阱。Token 解决"你是谁"，
> 但"你现在还能不能进来"必须查权威数据源（数据库）。代价是每个请求多一次主键查询，
> 换来的是权限变更**立即生效**。业界常见做法：短 TTL token + 每次校验，或维护
> `userId → token 列表`的反向索引在封禁时批量驱逐（本项目 Redis 是单向映射，做不到）。

### BUG-2【中等 · 逻辑】删除用户时漏删"其他成员挂在其知识库下的会话"

**根因** —— `JdbcAdminRepository.deleteUserCascade` 只删了被删用户自己的会话：

```java
deleteMessagesOfSessionsByUser(userId);
jdbcTemplate.update("DELETE FROM conversation_session WHERE user_id = ?", userId);  // 只删自己的
...
jdbcTemplate.update("DELETE FROM knowledge_base WHERE workspace_id IN "
        + "(SELECT id FROM workspace WHERE owner_user_id = ?)", userId);            // 删掉整个 KB
```

如果别人在被删用户的知识库下建过会话（协作场景必然发生），删 KB 时这些残留会话会触发：

```
ERROR 1451: Cannot delete or update a parent row: a foreign key constraint fails
```

由于方法带 `@Transactional`，**整批删除回滚**，后台"删除用户"直接 500。

**为什么原来没暴露**：当前库里所有工作空间都是单成员，没有跨用户会话，所以测不出来。
但这是一颗**定时炸弹**——一旦有多人协作就炸。

**修复** —— 删 KB 之前，先清掉这些 KB 下的**所有**会话（不限 user_id）：

```java
deleteMessagesOfSessionsByUser(userId);
jdbcTemplate.update("DELETE FROM conversation_session WHERE user_id = ?", userId);
// 关键：被删用户拥有的知识库里，可能还挂着【其他成员】建的会话。
deleteMessagesOfSessionsInOwnedKnowledgeBases(userId);
jdbcTemplate.update(
        "DELETE FROM conversation_session WHERE knowledge_base_id IN "
                + "(SELECT id FROM knowledge_base WHERE workspace_id IN "
                + "(SELECT id FROM workspace WHERE owner_user_id = ?))", userId);
```

**验证** —— 构造真实协作场景：

```
用户 A(id=33) 建工作空间 33 + 知识库 29
A 把 B(id=34) 加为成员          -> 201
B 在知识库 29 下建会话           -> 201
数据库确认：session 14，session_owner=34，ws_owner=33  ← 隐患成立
管理员删除用户 A                -> 200  ✅（修复前会 500）
```

> **面试点**：这正是「还有谁的外键指向我？」的工程落地。写级联删除时最容易犯的错，
> 就是**只按"归属人"维度删，忘了按"被引用资源"维度删**。正确顺序永远是：
> 先删所有指向目标资源的记录（不管它属于谁），最后删资源本身。

### BUG-4【轻微 · 内存泄漏】Python 文档锁字典无限增长

`processing.py` 的 `_document_locks` 用 `setdefault` 为每个文档建锁，**从不清理**，
长周期运行会随文档数持续累积。

**修复** —— 引用计数 + `finally` 释放（不能直接 `pop`，否则会出现
"一个线程等旧锁、另一个线程建了新锁"的竞态）：

```python
def _document_lock(knowledge_base_id, object_key):
    lock_key = f"{knowledge_base_id}:{object_key}"
    with _document_locks_guard:
        lock = _document_locks.setdefault(lock_key, Lock())
        _document_lock_refs[lock_key] = _document_lock_refs.get(lock_key, 0) + 1
        return lock

def _release_document_lock(knowledge_base_id, object_key):
    lock_key = f"{knowledge_base_id}:{object_key}"
    with _document_locks_guard:
        remaining = _document_lock_refs.get(lock_key, 0) - 1
        if remaining <= 0:
            _document_lock_refs.pop(lock_key, None)
            _document_locks.pop(lock_key, None)
        else:
            _document_lock_refs[lock_key] = remaining
```

`process_parse_task` 用 `try/finally` 包裹，保证异常路径也释放。

## 二、审查中核实过的 3 条（2 条误报 + 1 条后来被推翻）

这一节记录审查过程中被提出、**当时**经核实判为"不成立"的三条。
**其中第 2 条在后续阶段被推翻** —— 保留在这里，是为了记住一个教训：**「当前环境能跑」不等于「设计正确」。**

| 疑似问题 | 核实结论 |
|---|---|
| **Python 后台任务阻塞事件循环**（判为"严重"） | ❌ **误报**。审查者称"同步 BackgroundTask 不会进线程池"。实测查阅容器内 Starlette 1.6.0 源码 `background.py`：`is_async_callable(func)` 为假时走 `await run_in_threadpool(...)`，**同步函数确实会被丢进线程池**。实测连发 5 次请求，服务均立即响应。 |
| **`@Profile("local")` 导致生产环境认证缺失** | ⚠️ **当时判为"非 bug、已知设计"，这个结论已被推翻**（2026-09-19 阶段六 A 组）。当时的理由是「`deploy/docker-compose.yml` 里配了 `SPRING_PROFILES_ACTIVE=local`，能跑」——只回答了「现在会不会报错」，没回答「换个环境还成不成立」。实测：把 jar 放进**没有该环境变量**的容器，Spring Boot 直接 `APPLICATION FAILED TO START / Reason: Failed to determine a suitable driver class`（配置全锁在 `application-local.yml` 里）。已按真实缺陷修复：清除 24 个 `@Profile("local")` + 配置合并回 `application.yml`。详见 `docs/功能改进建议.md` 第五节末。 |
| **backend 健康检查端点不存在** | ❌ 不成立。`pom.xml` 含 `spring-boot-starter-actuator`，`application.yml` 暴露了 `health,info`，实测 9 个容器全部 healthy。 |

> **方法论提醒**：并行审查能快速覆盖大面积，但**审查结论必须核实**。
> 本次 4 个分组共报 15 条，其中 3 条（20%）当时被判为不成立。
> 而上面第 2 条又说明：**核实一次也不够。** 判一个设计问题为误报时，要问的是**「换个环境、换个前提，它还成立吗」**，而不只是**「现在有没有报错」** —— 这两句话看起来很像，但后者会把「靠一个环境变量兜着的缺陷」判成正常。

这些是真问题，但修复成本较高或影响有限，**暂不改动，仅记录**：

| # | 问题 | 位置 | 为什么暂不修 |

| 4 | **docker-compose 端口全暴露**：MySQL 3306、Redis 6379、MinIO 9000/9001、Milvus 19530 等全部映射到宿主机 | `deploy/docker-compose.yml` | 本地开发环境可接受；**上生产前必须收紧**（改 `127.0.0.1:3306` 或移除 ports） |
| 5 | **MinIO 客户端每次新建不关闭**：`processing.py` 每次下载 `new Minio(...)`，从不显式关闭，依赖 GC | `processing.py` | 高并发下连接池堆积，但当前负载下无影响 |
| 6 | **SSE 客户端断连未取消上游流**：`ConversationController.stream` 的 `CompletableFuture` 未注册 `emitter.onTimeout/onCompletion` 取消，客户端断开后上游仍读完（最多 90s） | `ConversationController` | 浪费线程与连接，不影响正确性 |

## 一、P0：Docker daemon 重启后，向量检索全链路瘫痪

**复现**（2026-10-24，Docker Desktop 冷启动后跑 e2e）：

```
e2e 上传文档 → 解析任务 FAILED
ai-service 日志：pymilvus.exceptions.MilvusException:
    Fail connecting to server on milvus:19530 ... Connection refused
docker inspect ai-copilot-milvus：RestartCount=45，每 10 秒重启一次（ExitCode=0）
```

**根因** —— `deploy/docker-compose.yml` 里 `etcd` 与 `milvus-minio` 两个服务**没有配置 `restart: unless-stopped`**，其余 7 个服务都有。Docker daemon 关闭时全部容器收到 SIGTERM；daemon 重新启动后，有重启策略的 7 个服务自己回来了，etcd 和 milvus-minio 永远停在 `Exited (255)`。Milvus 连不上元数据服务，陷入「启动 → 连 etcd 失败 → 干净退出 → restart」的循环。

**教训**：compose 里的 `restart` 策略是**逐服务**的，漏一处就是「下次重启全站挂一半」；而 healthcheck 全绿的 7 个服务掩盖了这两个没起来的依赖——**健康只说明「起来的都活着」，不说明「该起来的都起来了」**。

**修复**：补齐两个服务的 `restart: unless-stopped`；`docker compose up -d etcd milvus-minio` 后 Milvus 自行恢复 healthy，RestartCount 停止增长。

## 二、同一次复现暴露的第二个问题：重试预算撑不过一次依赖冷启动

Milvus standalone 从冷启动到 healthy 实测约 60-70 秒，而解析任务的重试预算是 `MAX_RETRIES=3 × 退避 2s`（指数退避 2+4+8 = 14 秒）。daemon 刚启动就上传的文档，注定在 14 秒内烧光重试、被判 `FAILED`——之后只有人工点「重试」才能救回。

**修复**：`AI_SERVICE_TASK_MAX_RETRIES=5`、退避基数 3s（3+6+12+24+48 ≈ 93 秒），覆盖一次完整的 Milvus 冷启动。原则：**重试预算的量纲要按「最长的暂时性故障」定，而不是按「最短的代码路径」定**。

## 二、事务边界重构：连接不再跨模型调用存活

**问题**（第一轮遗留 #1）：`ConversationService.streamAsk` 带 `@Transactional` 却在事务内调 ai-service 流式接口（readTimeout 90s）。数据库连接从方法开始被独占到结束，其中 95% 的时间在等模型吐字。HikariCP 默认 10 个连接——**10 个并发的流式提问就能让全站请求排队**。`askAgent`（Agent 调用）与 `KnowledgeService` 的检索/问答/上传登记同理。

**修法分三类，按「这里到底需不需要原子性」区分：**

| 场景 | 修法 | 放弃了什么 |
|---|---|---|
| **模型/检索调用**（`streamAsk`、`askAgent`、`KnowledgeService.search/answer`） | 直接删掉 `@Transactional`，各语句各自借还连接 | 「模型失败则用户消息回滚」。这笔原子性本来就是坏账：为回滚一条 INSERT 绑住连接 90 秒；且提问记录保留反而符合直觉（答错能看到「问过什么」，重试即可） |
| **上传登记**（`KnowledgeService.uploadDocument/registerDocument` 及解析状态三方法） | 同上删注解 | 顺带**修掉一个隐藏泄漏**：旧实现「MinIO 已上传 → 提交解析任务失败 → 事务回滚元数据」，对象成了没有任何行指向的孤儿，永远无法被删除流程清理。现在元数据保留为 UPLOADED，走「重新解析」即可恢复 |
| **管理后台级联删除**（`AdminService.deleteUser/deleteWorkspace/deleteKnowledgeBase`） | 远程清理移到事务外，**编程式 `TransactionTemplate` 把事务精确压在级联 DELETE 那一段** | 级联删除的多条 DELETE 必须整体原子（第四轮 BUG-2 的教训），不能简单删注解；声明式注解只能圈住整个方法，表达不了「只有这一步要原子」 |

> **方法论**：判断一个 `@Transactional` 该不该存在，问的是「这个方法里的多条语句之间有没有『要么都成立要么都不成立』的关系」，而不是「加上总没错」。加了没必要的注解不是更安全，是把连接池的容量送给了最慢的那次 HTTP 调用。

**顺带修掉的隐患**：`uploadDocument` 内部 `this.registerDocument(...)` 是自调用——Spring 代理不生效，`registerDocument` 的 `@Transactional` 从来没真正起过作用。删注解后这个「看起来有事务其实没有」的暗雷一并消失。

**测试**：新增 3 条用例钉住新行为——Agent 调用失败后用户消息保留且不 touchSession；流式失败只发 user 事件（绝不发 sources/complete 当成功）；管理后台级联删除在显式事务内执行（`getTransaction`/`commit` 被调用）。后端 **112 → 115** 全绿。

## 七、CI e2e job 排障：一次完整的「盲区→闭环」实战

三层单测 job 在 GitHub Actions 上**首次即全绿**；e2e job 连续四跑失败。最终根因出乎预料，排障路径每一步都值得记录：

1. **拆步定位**：把「构建+启动」拆成两个 step 后，步骤状态直接表明 **Build images ✅ / Start the full stack ❌**——失败在起容器，不在构建（这一步排除了一大半假设）。
2. **时长反证**：e2e job 全程 56 秒，失败发生在 up 的**秒级**——不是 Milvus 健康检查超时（那要分钟级），更像镜像拉取问题。
3. **日志盲区与注解回读**：Actions 的日志 API 对匿名请求返回 403（需要 repo admin），公开网页也要登录。解法：失败时把 up 的最后 30 行用 `::error::` 工作流命令**重新发射成注解**——注解 API 匿名可读。加上本地 git credential 的 API 认证，排障闭环从「猜」变成「读」。
4. **根因（注解里白纸黑字）**：`minio Error pull access denied for minio/minio, repository does not exist`——**MinIO 把 Docker Hub 上的官方镜像仓库删除了**。逐一验证三个渠道：Docker Hub API 返回 `object not found`（仓库确实没了）；quay.io/minio/minio 匿名拉取 401；连 dl.min.io 的下载路径都 410 Gone。本地一直能跑，只是因为用的是六周前拉下的旧镜像层——**「本地能跑」掩盖了「全新环境必挂」**，与第四轮「etcd 不自启」是同一类被本地缓存掩盖的部署缺陷。
5. **修法**：按官方 README 仅剩的指引（「自己 build Docker image」），从 GitHub Releases 下载 pinned 版本的二进制、`sha256sum -c` 校验后打包为自建镜像（`deploy/minio/Dockerfile`），minio 与 milvus-minio 共用。两个坑：① 校验文件里登记的文件名不带平台段（`minio.RELEASE...`），二进制必须存成同名才能 `sha256sum -c`；② 官方镜像的 ENTRYPOINT 是入口脚本而自建的是二进制本身，compose 的 `command` 写法随之不同（`server /path` 而非 `minio server /path`）。healthcheck 顺带从依赖 `mc` 改为 MinIO 自带的 `/minio/health/live` 端点。
6. **顺手加固**：milvus 健康检查补 `start_period: 120s`；`up` 带 3 次退避重试。

**结果**：修复推送后 CI **四 job 全绿**（e2e 1.9 分钟、三层单测共约 2 分钟）。本地全栈换自建 MinIO 镜像后，旧数据卷无缝复用，e2e 两连跑 exit 0、契约探针 33/33。

> **方法论**：从红到绿的整个链路——「失败半区拆分 → 失败时长反证 → 日志盲区的注解回读 → 渠道逐一验证 → 自建消依赖」——没有任何一步靠猜。这套动作本身就是本次排障最有复用价值的产出。
