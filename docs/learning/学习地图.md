## 七、已纠正的错误认知

| 原认知 | 事实 | 依据 |
| --- | --- | --- |
| 项目使用了 Spring AI | ❌ **不成立**。后端没有任何 `spring-ai` 依赖，也没有 `ChatClient`。模型调用由 Python AI Service 用标准库 `urllib` 直接发 HTTP，Java 侧用 `HttpURLConnection` 转发 | `backend/pom.xml` 依赖清单 + 全仓库检索 `spring-ai` / `ChatClient` 零命中 |

**核心技术教训（面试素材候选）**
1. **一个能推翻融合结果的弱重排器，比没有重排更糟。** 最初用「IDF 加权词覆盖率」做全局重排，Hit@1 反从 92.9% 掉到 89.3%。改为「加法提权」后——查询无标识符时加成恒为 0，排序完全等于融合结果，**不可能退化**。
2. **中文 bigram 的跨词噪声会污染覆盖率打分。** 「迁移脚本做了什么改动」切出 `了什`/`么改`，恰好命中另一篇文档的标题「索引做了什么」。所以重排只采信「含字母数字的标识符词元」。
3. **标识符必须同时产出整体 token 和分段 token。** 查询写 `V8`、文档写 `V8__add_source_retriever`，只产整体 token 时两边永远匹配不上，而 `v8` 恰恰是最有区分度的词。
4. **展示分数不能用 `min(score, 1.0)` 截断** —— 会让所有命中标识符的片段并列「相关度 1.00」。要按本轮最高分重新缩放。
5. **评估集本身必须被审查。** 修了两次：文档级判分 → chunk 级判分（否则所有方案都是 100%，测不出差异）；只认编号 → 编号 + 答案文本（否则「只罗列型号的目录片段」和「被切片截断的残句」都会被误判成命中）。**指标下降的不是系统，是原先虚高的部分被挤掉了。**

**环境坑 6（重要）**：`docker cp` 是往容器里部署改动的唯一手段（Docker Hub 不可达），**一旦 `docker restart` 之外的 `--force-recreate` 发生，所有 cp 进去的改动全部丢失**。因此源码必须始终以宿主机 `D:\ai_project\AI_agent` 为准。

**核心技术教训（面试素材候选，优先级从高到低）**

1. **切片的本质是「保留结构」，不是「控制长度」。** 旧实现第一行 `" ".join(text.split())` 就把换行压平，段落边界当场丢失；再按固定字符等距切，必然把语义单元从中间切断（错误码条目被切成不相连的两半、表格行从列中间断开）。**结构信息必须在抽取阶段就带出来**（`heading_path`），切片阶段才有边界可用——只在块边界上打包，标题变化是硬边界，只有单块自己超长时才退化成字符滑窗。
2. **给 chunk 加标题前缀，比调 overlap 更有效。** overlap 是「碰运气让答案别正好落在切口上」；标题前缀是「确定性地让每个片段自带上下文位置」。代价几乎为零（每片多几十个字符），但对向量检索的作用是结构性的——纯向量 Hit@1 +17.9pp、语义题从 87.5% 升到 100%，主要来自这里。
3. **表格要「按行成块 + 每块重复表头」。** 一行一个块，形如 `型号: XZ-2500 | 默认限流: 每秒两百次`。整表当一段文本会行列错位，按字符滑窗切会让表头和数据分家；一行一块则每片都**语义完整且自解释**。
4. **切片粒度会同时影响两路召回的相对强弱。** 切片变细后纯关键词小幅回落 3.6pp（恰好 1 道题），因为候选片段变密、相似片段间的 BM25 分差缩小。两路不是各自独立的——调切片参数时两路要一起看。
5. **指标异常时，先怀疑测量，再怀疑系统。** 详见下一条。
6. **判分口径只允许有一份实现。** 评估脚本和自检脚本如果各写一份「算不算命中」，只要有一边改了口径，就会出现「评估说 MISS、自检说可答」这种自相矛盾的结论——而自检的全部意义正是给评估提供独立但**同口径**的证据。

**方法论记录：一次「指标在说谎」的排错（重点）**

切片改完重跑评估，同一份代码、同一份评估集连续跑出三组互相矛盾的数字：

| 轮次 | Recall@5 | MRR（vector/keyword/hybrid） | Hit@1 |
|---|---|---|---|
| 1 | 100 / 100 / 100 | 85.2 / 90.8 / 97.6 | 75.0 / 85.7 / 96.4 |
| 2 | 96.4 / 100 / 96.4 | 84.0 / 91.7 / 96.4 | 75.0 / 85.7 / 96.4 |
| 3（最终） | 100 / 100 / 100 | 87.6 / 91.7 / 100.0 | 78.6 / 85.7 / 100.0 |

同一道题（`覆盖索引为什么能变快`）在 vector 与 hybrid 两路都 MISS，但在 keyword 里排 #1 —— 这个组合**非常像向量索引里那条数据丢了**。最初怀疑 Milvus 主键复用竞态（chunk id = `sha256(object_key:index)`，重新切片后下标 0 会复用同一主键，而「按主键删除 + 插入同一主键」是 Milvus 的经典问题）。

排查步骤（每步都用独立证据，不靠推断）：

1. **直接查库**：判分目标片段确实存在，只有 1 条；
2. **直接向量检索**：绕开混合检索单独调 `vector_search`——该片段排**第 1 位**（score 0.7475）。**假设被证伪**；
3. **反向验证**：把 28 道题的判分串与库里全部 chunk 做**纯字面匹配**（完全不经过向量/BM25）——28 题全部命中；
4. **看进程**：容器里**同时有两个重索引脚本在跑**。

真实原因是：我用 `docker exec` 启动的重索引脚本被工具超时中断，但**容器内的 python 进程并没有随之退出**，两个循环同时对同一批文档执行「先删旧 chunk → 再写入新 chunk」，互相覆盖。表现出来就是「某文档切片数在两轮间从 5 变 0」「某文档整篇从对象列表里消失」（重索引脚本从 Milvus 取 object_key 列表，那篇此刻恰好是空的，于是报出「9 篇文档」）。

**由此固化成两条索引可信度验收标准**（已写进 `scripts/verify_index.py`，每条评估前必过）：

| 证据 | 证明什么 | 不过关意味着 |
| --- | --- | --- |
| 连测 3 次 chunk 总数与逐文档分布完全一致 | 索引「没在变」 | 有并发写者 |
| 每道题的判分串与库里全部 chunk 字面匹配 0 缺失 | 索引「答案真的在里面」 | 语料缺失或入库失败 |

第二条比第一条更强：计数一致只说明稳定，字面命中才说明内容对。**如果当时直接去改 `index_chunks` 的主键生成逻辑（那是个看起来完全合理的改动方向），就会白改一版代码**——而且因为并发窗口是随机的，改完还可能「看起来好了」。

**环境坑 9（重要，本次踩了两次）**：工具超时不等于容器内进程结束。`docker exec` 启动的进程在宿主机客户端被杀后**不会一起退出**，会变成孤儿继续跑。可靠做法是用 `docker exec -d` 分离运行，输出重定向到文件后再 `docker cp` 取出；并且要加 `python -u`，否则重定向时是块缓冲，文件在进程退出前一直是空的。观测索引前先列一遍容器进程（容器内没有 `ps`，可读 `/proc/*/cmdline`）。

**环境坑 10**：`_recover_tasks_loop` 是**每 5 秒轮询**的循环（不是只在启动时跑一次），会反复捞 `ACCEPTED` / `RETRYING` / 超时 `PROCESSING` 的任务重跑。做索引观测前必须先清掉残留的未完成任务行。另外 `task_processing_stale_seconds = 300` 小于大文档的解析耗时，可能触发对同一文档的重复处理（进程内 `_document_lock` 保证了正确性，但会重复消耗 embedding 调用）——这是阶段六可优化的点。

**环境现实**：容器内 openpyxl / xlrd / python-pptx / bs4 / html5lib 全部装不上（PyPI 不可达）。所以 xlsx / pptx 用标准库 `zipfile` + `xml.etree` 直接解析 OOXML，代价是要自己处理：共享字符串表回填（`<c t="s"><v>7</v></c>` 里的 `7` 是下标）、工作表物理文件名映射（由 `xl/_rels/workbook.xml.rels` 决定，不能假设第 N 个是 `sheetN.xml`）、Excel 列名的 26 进制无 0 规则（A=1 … Z=26, AA=27）。

**三个「只有端到端测试才能发现」的设计缺陷（面试素材候选）**

1. **模型把文件名当成 `document` 传。** `list_documents` 里显示的是 `inspection-robot.md`，真正的取值是 `kb/32/<uuid>/inspection-robot.md`。模型看到什么就传什么。

2. **轮数用尽时把已取回的证据全丢掉了。** 模型很爱探索（一次提问连发 4 个工具调用很常见），3 轮烧光后代码直接返回「达到最大工具调用次数」——而对话里已经攒着 4 条命中片段。

#### 变更 1：清除 24 个类的 `@Profile("local")`（← 学习地图「三、Spring Boot」那行引用的就是这里）

#### 变更 2：`task_processing_stale_seconds` 导致大文档被重复解析

**原先的怀疑是错的**：本以为是「`updated_at` 没跟着走」——但查 `V4__create_document_processing_task.sql` 发现它是 `ON UPDATE CURRENT_TIMESTAMP`，看起来没问题。

**真实成因（更微妙）**：`ON UPDATE CURRENT_TIMESTAMP` **只在「同一行里其他列的值真的发生了变化」时才触发**。而解析期间：

- `_set_task(task_id, "PROCESSING", None, task.retry_count)` —— status 本来就是 PROCESSING、`failure_reason` 本来就是 NULL、`retry_count` 也没变 → MySQL 眼里这是**空操作**，时间戳原地不动；
- 真正的耗时段 `index_chunks` 内部全是网络调用，中间**一条 SQL 都不发**。

于是：文档解析超过 300s → 恢复循环的 `find_recoverable` 判定它是僵尸任务 → **从头再做一遍**（重新下载、重新切片、重新调 embedding 接口）。**静默花掉一倍的钱**，且只在「文档够大」时暴露。而两个线程确实并存：上传走 FastAPI `BackgroundTasks`（线程池），恢复循环走 `asyncio.to_thread`。

**改法**：处理期间加**心跳线程**（`_TaskHeartbeat`，每 `stale/4` 秒续期一次），把 `updated_at` 的语义从「最后一次状态变更」改成「最后一次存活上报」—— 只有真正挂掉的进程才会停止上报、才会被回收。另外把 `claim` 改成显式 `SET status = 'PROCESSING', updated_at = NOW()`（顺手拆掉「空操作不更新时间戳」这个陷阱）。

**为什么必须是后台线程**：耗时段是 `index_chunks` 内部的网络调用，中间没有可以让出来的位置，没法「顺手更新一下」。

**新增测试 11 个**：`tests/test_task_store.py`（6 个，用假连接断言发出去的 SQL 里真的有 `updated_at = NOW()`）+ `tests/test_processing.py`（5 个，其中一个是回归测试：心跳间隔被压到 0.01s、`index_chunks` 故意慢 0.15s，断言期间真的发出过心跳、且结束后立刻停止）。

### 2026-09-19 阶段六 C 组：工程化补齐（功能开发，非教学）

四项一起做：**限流**（登录爆破 + LLM 接口防刷）、**分页**（会话与消息）、**前端测试框架**（vitest）、**多标签页状态同步**。

#### 通用分页原语（可迁移的接口设计知识）

新增 `common/api/PageQuery` 与 `PageResponse<T>`，只做两件事：**归一化输入** 和 **描述结果**。

| 外部输入 | 如果不处理会怎样 | 处理方式 |
|---|---|---|
| 不传 `page` / `size` | 前端不改就没法用 | 给默认值 `0` / `20` |
| `page=-3` | 传给 SQL 直接报错 | 归零 |
| `size=0` | 变成「每页 0 条」，接口永远返回空数组，**看起来像没有数据** | 退回默认值（而不是当成「返回 0 条」） |
| `size=1000000` | 一次把整张表捞进内存 —— **用一个 query string 把「分页」直接打成 DoS** | 压到上限 `MAX_SIZE = 100` |
| `page=100000000` | `page * size` 用 `int` 相乘会溢出成负数 | `offset()` 返回 `long` |

> 口诀：**凡是能控制「返回多少数据」的参数，都必须有上限。**

`PageResponse` 里 `hasNext` 是**冗余字段**（可由 page / size / totalElements 算出），但刻意保留 —— 前端判断「要不要显示加载更多」是最高频操作，让它少算一次就少一处算错。

**一个很容易写错的边界**：`hasNext` 必须只由 `(page+1)*size < totalElements` 决定，**不能用 `items.size()` 去推**。用 `items.size()` 在「最后一页不满」且查询里有过滤时会把最后一页也算成「还有下一页」，前端于是显示一个点进去永远为空的「加载更多」。这一条专门写了测试钉住。

#### 分页：为什么页号要「从最新往回数」

聊天消息流**不能**用列表分页的直觉：如果 `page=0` 返回的是**最早**的 20 条，用户打开一个长会话只能看到开头几个月前的寒暄，还得一路点到最后一页。

所以仓储方法是「`ORDER BY created_at DESC, id DESC LIMIT ? OFFSET ?` 再在 Java 里翻回正序」—— `offset=0` 就是最近的一批，`offset` 越大越古老。

**⭐ 由此得到一个漂亮的复用**：`findMessages(sessionId, 20, 0)` 同时是「界面第一页」**和**「送给模型的历史上下文窗口」。之前 `ask` / `askAgent` / `streamAsk` 把**整个会话的全部消息**喂给模型 —— 一个聊到 200 轮的会话每次提问都要重新计费 400 条消息，越聊越贵、越聊越慢、最后撞上下文窗口报错。现在统一走 `recentHistory()`，界面翻页与上下文窗口共用一个查询，只是 offset 不同。

#### 分页实现里踩到的坑：`LIMIT` 作用在**行**上，不是**消息**上

原来的 `findMessages` 用 `LEFT JOIN conversation_message_source` 一次查出来再在 Java 里按 id 分组 —— 一条消息有 N 个来源就展开成 N 行。此时加 `LIMIT 20`，限制的是**行数**，实际可能只取到 3 条消息，分页彻底失真。

**改法：两步查。**
1. 先取消息主体（`LIMIT`/`OFFSET` 作用在 `conversation_message` 上，语义才正确）；
2. 再按这批 id 用 `WHERE message_id IN (?,?,…)` 批量补来源与执行轨迹（占位符动态拼、值仍走参数绑定，不存在注入）。

顺带干掉了原来那个「用 `LinkedHashMap` 去重」的分组逻辑 —— 它是为了修补 JOIN 造成的行膨胀而存在的，问题从源头解决后就不需要了。

#### 多标签页状态同步：一个「两边各缺一块、拼起来正好漏掉」的洞

现象：A 标签登出后，B 标签仍然显示已登录。

根因是两条事件机制各自的性质：

| 机制 | 是否跨标签页 |
|---|---|
| `localStorage` 的 `storage` 事件 | ✅ 跨标签页，但**只派发给「其它」标签页** —— 写的那一方自己收不到 |
| `dispatchEvent(new Event(...))` 自定义事件 | ❌ **只在本标签页内传播** |

项目里已有的 `aicopilot-auth-changed` / `aicopilot-workspace-changed` 都是第二种。于是：A 清 localStorage + 派发自定义事件 → A 自己正常；B 既没监听 `storage` 事件、又收不到自定义事件 → 仍然显示已登录。

**修法是「架桥」而不是「改监听者」**：新增 `crossTabSync.ts`，监听 `storage` 事件后**翻译成本项目已有的自定义事件**再派发。这样 App.vue / HomeView / ChatView / DocumentsView / KnowledgeView 这 5 个既有监听者**一行都不用改**就获得了跨标签能力。

`StorageEvent` 的三个判定维度（都写了测试）：`event.key`（`null` 表示 `clear()`）、`event.newValue`、`event.storageArea`（要排除 `sessionStorage`）。

顺带在 `App.vue` 里加 `syncWorkspaceFromStorage` 时，**幂等性检查是关键**：本标签自己切工作区也会派发同一事件，此时 ref 已经等于 localStorage 里的值 → 直接 return，不会多打一次接口。

#### 限流：为什么「只统计失败」和「先过闸门再比密码」

- **只统计失败**：如果每次请求都计数，一个正常用户在 15 分钟里刷新登录页 5 次就会被自己锁住。所以成功登录会 `clear()` 计数。
- **先过闸门再比密码**：被限流时连 `bcrypt` 都不算 —— 既省 CPU（顺手挡掉「用爆破拖垮 CPU」），也不给攻击者任何「这个密码对不对」的反馈。
- **限流的维度是「邮箱」而不是「IP」**，这是有意识的取舍：按邮箱记，攻击者无论换多少代理都拦得住（代价是攻击者可以故意把某账号锁 15 分钟，一种 DoS，但窗口很短且只影响登录、不影响已登录会话）；按 IP 记则换代理即绕过。生产环境通常两个维度都上。
- **邮箱要先归一化（`trim().toLowerCase()`）再计数**，否则 `ALICE@x.com` 换着大小写写就能绕过 —— 有测试专门钉这一条。

**数据结构上的一个关键决定**：`consume()` 用**单次原子自增的返回值**做判断，而不是「先 `get` 判断、再 `put` 写回」。后者是「读-改-写」三步，两个并发请求会同时读到 3、各自写回 4，**两次尝试只被记成一次** —— 限流器在临界点上少数，等于给攻击者一把倍速钥匙。所以给 `CacheService` 加了 `increment(key, ttl)`（Redis 的 `INCR` 是单线程原子的）。有测试用 `spy` 断言「`increment` 调了 1 次、`get` 一次都没调」。

**⭐ 一个限流器最经典的翻车点**：过期时间**只在第一次自增时设置**。

```
if (value == 1L) redisTemplate.expire(key, ttl);
```

如果每次自增都 `expire`，窗口就会被持续访问不断续命、永远不归零 —— 限流从「临时拦截」变成「**永久封禁**」。有专门的测试断言「第二次自增时 `never()).expire(...)`」。

**关于「Redis 挂了怎么办」**：这里**不做 fail-open**（不吞异常放行）。因为本项目的 Redis 本来就在鉴权链路上（每个请求都要用它校验 token），没有 Redis 时登录和调接口全都跑不通 —— 此时让限流器单独降级成不设防并不能让系统可用，只会让故障更难发现。真正要做的运维动作是给 Redis 加副本，而不是在应用层假装它没坏。

**为什么把「LLM 接口的扣配额」放在 Controller 而不是 Service**：**流式接口**要求这个判断发生在**打开 SSE 连接之前**。一旦进了异步线程再抛限流异常，HTTP 响应头早就发出去了，想拒绝只能改成往事件流里塞一个 `error` 帧 —— 前端拿不到 429，也就分不清「我被限流了」和「模型调用失败了」，提示语和重试策略都会写错。

### 2026-09-20 阶段六 B 组：查询改写（Multi-Query）+ 新格式纳入评估集（功能开发，非教学）

**测试基线**：ai-service **172 → 211 个用例**（新增 28 个查询改写 / 多查询融合用例 + 3 个评估脚本用例，另有 8 个把既有防御缺口补上后转绿的用例）。

#### ⭐ 本次最核心的产出是两条**方法论**，不是功能本身

**方法论 1：一个功能，不能在一个「它不可能失败」的题集上被验证。**

查询改写跑现有 28 题评估集，结果是 **变好 0 题 / 变差 0 题 / 不变 28 题**。看着像「这功能没用」，但真实原因是：**那批题的问法是从语料里抄的**（问「慢查询日志」「覆盖索引」「最左前缀」），BM25 靠字面就能命中，hybrid 已经是 100% Hit@1 —— **天花板到了，任何改动都不可能更好**。

→ 于是另做 `questions-paraphrase.json`：语料、判分口径、知识库**全都不变**，**只把提问改成真实用户的口语**，并且刻意不使用语料里的任何术语（说「回原本那张表」不说「回表/主表」，说「单独查后一个字段」不说「最左前缀」）。
→ 这才测出真实差异：hybrid Hit@1 **41.7%**，改写 **58.3%**。

**方法论 2：不可复现的机制必须跑两次，并把「稳定的收益」和「不稳定的收益」分开。**

改写是模型按温度 0.8 生成的，**不可复现**。跑两次：

| 模式 | Recall@5 | MRR | Hit@1 |
| --- | ---: | ---: | ---: |
| vector | 91.7% | 61.8% | 41.7% |（两轮**逐题完全一致**）
| keyword | 83.3% | 55.8% | 41.7% |（两轮**逐题完全一致**）
| hybrid | 91.7% | 63.2% | 41.7% |（两轮**逐题完全一致**）
| rewrite 第 1 次 | **100%** | 75.7% | 58.3% |
| rewrite 第 2 次 | **100%** | 62.5% | 33.3% |

- 前 3 列两轮逐题一致 → 索引没变、非 LLM 路径是确定性的，**波动只来自改写**（这是一个很干净的对照）。
- **稳定信号：Recall@5 91.7% → 100%**（原本完全没召回的那题被救回来），两次都复现。
- **不稳定信号：MRR / Hit@1**（58.3% vs 33.3%，baseline 恒为 41.7%）。

→ 最终决定：**默认不开**（`query_rewrite_enabled: bool = False`）。理由写进了 settings.py 的注释：稳定改善的只是「有没有捞到」，不能稳定改善「排得够不够前」，还要每次提问多打一次模型。要开需要**更大题集 + 多次运行取平均**，而不是在 12 道题上给融合权重调参 —— 那正是第六节踩过的坑（拿小样本拟合弱机制）。

#### 查询改写的实现要点

| 要点 | 说明 |
|---|---|
| **架构位置** | `multi_query_retrieve` 架在 `hybrid_retrieve` **之上**，不改它 —— 对「原问题 + N 条改写」各跑一遍完整单查询检索，再对这几份排名做**第二次 RRF**。因为 RRF 只看名次，「每份排名内部怎么排的」不影响正确性，单查询那条链路一行都不用改（它有 8 个既有测试在钉行为） |
| **用原问题重排** | 融合后重排用的是**用户的原始提问**，不是某条改写 —— 改写负责「多召回」，相关性仍由用户真正问的那句话定义。拿改写去重排等于让模型替用户决定什么算相关 |
| **必须 fail-open** | 改写在检索**之前**。`rewrite_query` 在任何异常下都返回**空列表**（调用方理解为「只用原问题」）。没 key / 超时 / 返回乱码时，系统行为与「没有这个功能」**逐字节一致**。这不是兜底代码，是这个模块唯一正确的失败语义 |
| **解析要防脏输出** | 模型很爱加 `1.` `-` 编号前缀（提示词说了不要也没用）。`_strip_decoration` 统一剥离；同时丢掉空行、与原问题重复的（大小写不敏感）、过长（>200 字，说明它在解释或答题）的行。注释里写明：**提示词负责「尽量」，解析负责「一定」** |
| **降低温度会毁掉功能** | 改写用 **temperature 0.8**（作答是 0.2）。温度太低时模型会反复给出几乎相同的句子，等于没改写 |
| **标识符必须原样保留** | 提示词明确要求「编号、型号、版本号、错误码必须原样保留」——一旦模型把 `ERROR 1451` 改写成「外键约束错误」，BM25 那一路就全废了。有单测钉这条提示词 |
| **Agent 路径显式关闭** | `agent_tools.knowledge_search` 传 `rewrite=False`：那里的 query 是**模型自己写的**，而且它会跨轮换措辞重试 —— 它本身已经在做多查询了。工具内部再套一层 = 每轮多打一次模型，收益高度重叠。有单测钉这个参数 |

#### 顺带修掉的两个既有防御缺口（`test_indexing.py` 里原本就是红的）

跑测试时发现 5 个失败，先**确认与本次改动无关**（改动只碰了 `retrieve_chunks` 的签名，而失败的两处分别在 `index_chunks` 与 `_fetch_corpus`/`document_inventory`），再看代码确认是「测试写好了、实现没做」的真缺口，于是补上：

| 缺口 | 后果 | 修法 |
|---|---|---|
| `content` 字段是 `VARCHAR(4096)`（按**字节**算），但 `index_chunks` 直接入库 | 超限时 Milvus **整批 insert 失败** → 整个文档入库挂掉 | 新增 `split_oversized_content`：按**字符**遍历切分（`chunk[:max_bytes]` 会把 3 字节汉字/4 字节 emoji 劈成非法 UTF-8 序列），保证「拼回去 == 原文」且「尽量塞满」 |
| Milvus 的 `query` 有硬上限 `offset + limit ≤ 16384` | 语料一超过这个量就抛 `query results exceed the limit size` → **小知识库一切正常、大一点整体检索失败**，最难复现的一类 bug | 抽出共用的 `iter_all_rows`：先用 `query` + offset 分页（常见路径、最稳），超限才改用 `query_iterator` 游标重来；`finally` 里必须 `close()` |

→ **一般化教训**：看到失败的测试，**先确认它是不是自己的改动引起的**（看失败点是否落在改动路径上），再决定是回退还是修 bug。这两条恰好是「测试走在实现前面」的例子 —— 测试是对的，实现缺了。

#### 新格式纳入评估集

- 语料：`docs/rag-eval/build_new_format_corpus.py` **用标准库手写 OOXML** 生成 xlsx/pptx，另加 csv/html 纯文本。为什么手写：二进制文件在 code review 里是黑箱，写成脚本后语料的**每一句事实**都可读可 diff；而且与 ai-service 的解析器（同为标准库实现）保持同一依赖水平。
- 自检的关键点：**判据必须是「切片后的 chunk 正文」，不是「块正文」**。标题（`<h2>`、幻灯片首页、工作表名）不进块正文，它进 `heading_path`、切片时被拼成前缀写进 chunk。第一版自检只查块正文，把「V16」「交接班流程」两个**确实能被检索到**的事实误报成缺失 —— **查错了对象，比不查更误导**。
- 语料构建走**真实 HTTP 链路**（`scripts/build_eval_knowledge_bases.py`：注册评估账号 → 建库 → 上传 → 轮询解析完成），不是直接塞 Milvus。
- **结果：13 题全部被四档模式召回（Recall@5 = 100%）**，表格类 7 题 + 网页类 3 题 Hit@1 全 100% → 「xlsx/pptx/csv/html → 解析 → 结构化切片 → 入库 → 检索」整条链路打通。

#### 顺带发现：小语料上融合反而拖后腿

新格式库只有 **10 个 chunk**，结果 **hybrid Hit@1 92.3%，纯向量和纯 BM25 各 100%** —— 融合丢了一题的第一名。原因：融合的价值来自「两路互补」，语料小且内容彼此高度不同时，两路本来就都对，融合只是在给**本来就正确的排序引入扰动**。与第六节「弱重排器比没有重排更糟」同类。
→ **评估结论必须带上语料规模。**

### 课程 17.2 思考题 · Tool Schema（2026-09-19）

| # | 题 | 我的回答 | 判定 |
|---|---|---|---|
| Q1 | 模型能看到工具代码吗？靠什么决定怎么用？ | 「不能」 | ✅ |
| Q2 | `description` 必须写清哪三件事？ | 「何时用、何时不用、参数从哪来」 | ✅ |
| Q3 | Schema 写了 `maximum: 8`，模型传 `limit=100000` 会怎样？ | 「检验」 | 🟡 方向对未说清 |

**Q3 正确答案**：**模型会无视它，照传不误** —— 因为服务器**根本不校验这个 Schema**，它只是随请求一起发给模型的**文字建议**。
→ 唯一生效的是代码里的 `clamp_limit`（`agent_tools.py:91`）：`min(max(int(value), minimum), maximum)`；非法类型（如字符串）则回退默认值。
→ 后果（注释原话）：「否则一个 `limit=100000` 就能把知识库拖垮」—— 扫 10 万条向量 + 拼进上下文，接口卡死 + 账单爆炸。

**核心口诀（已教）**：**Schema 是"说明书"，代码是"门禁"。**
说明书告诉模型怎么做对；门禁保证它做错时也出不了事。**永远不要信任外部输入** —— 模型给的参数与用户填的表单同等不可信。

### 课程 17.2 已教素材（复用）
- **Tool Schema = Python 函数 + JSON Schema**，模型看不到代码，**只读 `description` 这段自然语言**。

- 本项目 `knowledge_search` 的 description 实写五层含义：这是什么工具 / 何时用（事实型问题）/ 强制约束（不凭记忆作答）/ 工具配合顺序（先 `list_documents`）/ 参数来源（必须取原值，别自己拼路径）。

### 课程 1.6 关键素材（复用）
- **会话三层结构**：`conversation_session` → `conversation_message`（靠 `session_id`）→ `conversation_message_source`（靠 `message_id`）。引用来源单独建表的原因：一条回答可引多个片段，塞进 message 就无法按 score 排序/单独查。
- **会话搜索真实 SQL**（`JdbcConversationRepository.java:53`）：`title LIKE ? OR EXISTS (SELECT 1 FROM conversation_message m WHERE m.session_id = conversation_session.id AND m.content LIKE ?)`。用 `EXISTS` 而非 JOIN 的原因：命中即停，不必捞出全部消息。
