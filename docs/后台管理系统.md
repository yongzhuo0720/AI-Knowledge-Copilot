# 后台管理系统（Admin Console）

> 用途：集中管理全系统的账号、工作空间与知识库。
> 位置：前端 `/admin` 路由（侧边栏底部 `⛨ Admin` 入口，**仅管理员可见**）。

---

## 一、登录方式

登录页（`/knowledge`）有**三个入口**，把普通用户和管理员分流：

| 入口 | 标题 | 按钮 | 说明 |
|---|---|---|---|
| **普通登录** | 登录工作台 | 登录工作台 | 所有正常账号，登录后进入业务页面 |
| **管理员登录** | 管理员登录 | 进入管理后台 | 会**强制校验**管理员身份，登录后直接跳 `/admin` |
| 注册 | 创建你的账号 | 创建账号 | 注册新账号（注册出来的都是普通用户） |

**管理员登录的实际行为**（这是重点，不是纯 UI 分流）：

| 场景 | 结果 |
|---|---|
| 管理员账号 + 普通登录 | ✅ 成功（管理员首先也是普通用户） |
| 管理员账号 + 管理员登录 | ✅ 成功，自动跳转 `/admin` |
| **普通账号 + 管理员登录** | ❌ **401 拒绝**，提示"该账号不是管理员，无法进入管理后台。" |
| 密码错误 + 管理员登录 | ❌ 401，提示"邮箱或密码错误" |

注意最后两项的区别：**密码错的时候不会告诉你"你不是管理员"**，因为那等于变相确认"这个邮箱确实存在"。必须先证明"你是谁"，再检查"你够不够格"——顺序反了就是信息泄露。

### 后端实现

`LoginRequest` 加了一个**可选**字段 `admin`：

```java
public record LoginRequest(
        @NotBlank @Email String email,
        @NotBlank String password,
        Boolean admin      // 可选；null / false = 普通登录
) {
    public LoginRequest(String email, String password) {
        this(email, password, false);
    }
    public boolean requiresAdmin() {
        return Boolean.TRUE.equals(admin);
    }
}
```

`AuthenticationService.login` 里的新增校验：

```java
User user = userRepository.findByEmail(...)
        .filter(candidate -> "ACTIVE".equals(candidate.status()))
        .filter(candidate -> passwordEncoder.matches(request.password(), candidate.passwordHash()))
        .orElseThrow(() -> new AuthenticationException("invalid email or password"));
// 先证明「你是谁」，再检查「你够不够格」——顺序不能反，否则会泄露账号是否存在。
if (request.requiresAdmin() && !user.admin()) {
    throw new AuthenticationException("administrator privilege is required");
}
```

**向后兼容**：老客户端不传 `admin` 字段时为 `null`，按普通登录处理，原接口行为完全不变。

## 二、"管理员"是怎么定义的

系统原本**没有**管理员概念，所有用户完全平等。本次新增了 `app_user.is_admin` 字段（Flyway `V7` 迁移）：

```sql
ALTER TABLE app_user
    ADD COLUMN is_admin BOOLEAN NOT NULL DEFAULT FALSE AFTER status;
```

**为什么不用"硬编码 userId == 1"？**
因为那在面试里答不出手。真实企业做法是**数据驱动**：权限是数据库里的一列，可以随时授予/撤销，而不是写死在代码里。

**升级引导**：V7 带了一段 UPDATE，仅当系统当前**一个管理员都没有**时，把最早注册的账号提为管理员——避免升级后无人能进后台。

## 三、三层安全设计（这是最该讲清楚的部分）

请求要进后台，必须连过三关：

| 关卡 | 位置 | 不通过的后果 |
|---|---|---|
| ① 有没有登录？ | `AuthenticationInterceptor` | 401 `AUTHENTICATION_REQUIRED` |
| ② 是不是管理员？ | `AdminService.requireAdmin` | 403 `ACCESS_DENIED` |
| ③ 操作合不合规？ | `AdminService` 业务校验 | 400（各种 BusinessException code） |

**关键点**：① 依赖 `AuthenticationWebConfiguration` 里的这一行——

```java
registry.addInterceptor(authenticationInterceptor)
        .addPathPatterns("/api/v1/workspaces/**", "/api/v1/knowledge-bases/**", "/api/v1/admin/**");
```

**漏加 `/api/v1/admin/**` 的话，新接口完全裸奔**：请求根本到不了 `requireAdmin`，因为 intercept 阶段就被放行，`operatorId` 取到 null，整个权限体系失效。这是本项目加新模块时最容易漏的一步。

### ② 的实现细节

```java
private void requireAdmin(Long operatorId) {
    if (operatorId == null) {
        throw new AccessDeniedException("authentication is required");
    }
    User operator = userRepository.findById(operatorId)
            .orElseThrow(() -> new AccessDeniedException("authenticated user does not exist"));
    if (!operator.admin()) {
        throw new AccessDeniedException("administrator privilege is required");
    }
}
```

注意它是**每次请求都查一次数据库**，而不是信任前端传来的"我是管理员"标记——前端可以被篡改，服务端判定才作数。

### ③ 的三个业务护栏

| 场景 | 错误码 | 为什么必须拦 |
|---|---|---|
| 封禁/删除/降权**自己** | `SELF_OPERATION_FORBIDDEN` | 管理员手滑把自己封了，就再也进不来后台了 |
| 撤销/删除**最后一个**管理员 | `LAST_ADMIN_PROTECTED` | 系统会永久失去管理能力，只能改数据库救场 |
| 操作不存在的用户 | `RESOURCE_NOT_FOUND` | 明确报错，不静默成功 |

## 四、能做什么

### 用户账号
- 查看全部用户（账号、邮箱、状态、权限、资源占用、注册时间）
- **封禁 / 解封**（改 `status`）
- **授予 / 撤销管理员**（改 `is_admin`）
- **删除用户**（连带其名下工作空间、知识库、文档、会话）

> **封禁为什么能真的挡住登录？**
> 因为 `AuthenticationService.login` 里早就有这一句：
> ```java
> .filter(candidate -> "ACTIVE".equals(candidate.status()))
> ```
> 把 status 改成 `SUSPENDED`，这个 filter 就直接把用户挡在门外了。**不用改任何登录代码**——这就是数据驱动权限的好处。

### 工作空间
- 查看全部工作空间（名称、归属人、成员数、知识库数）
- 删除工作空间（连带其下知识库、文档、会话）

### 知识库
- 查看全部知识库（名称、所属空间、文档数、会话数）
- 删除知识库（连带其下文档、会话）

## 五、级联删除：外键课的真实工程落地

这是本次最有技术含量的部分，也是**"还有谁的外键指向我？"这个思维模型的实际应用**。

直接 `DELETE FROM app_user WHERE id = 25` 会怎样？数据库会拒绝：

```
ERROR 1451: Cannot delete or update a parent row: a foreign key constraint fails
```

因为 `workspace.owner_user_id`、`workspace_member.user_id` 都指向它。**必须先删干净所有指向它的子表数据。**

### 用户级联删除的完整顺序（不可调换）

```
conversation_message_agent_step        ← 最深
conversation_message_source            ← 最深
    ↓
conversation_message
    ↓
conversation_session
    ↓
document_processing_task
    ↓
knowledge_document
    ↓
knowledge_base
    ↓
workspace_member
    ↓
workspace
    ↓
app_user                               ← 最后才轮到它
```

规律：**从叶子往根走，永远先删"引用别人的"，最后删"被引用的"。**

代码里把最深两张表的删除抽成了 `deleteAgentStepsAndSources(sessionIdSql, parameter)` 复用——因为用户级联、工作空间级联、知识库级联三种场景都要删这两张表，只是定位 session 的条件不同。

|---|---|---|
| GET | `/api/v1/admin/overview` | 全站统计指标 |

全部要求 `Authorization: Bearer <token>`，且当前用户必须是管理员。

## 七、面试表达（1 分钟版）

> "我在项目里加了一个后台管理系统。权限模型上我没有硬编码，而是给用户表加了一个 `is_admin` 字段，用 Flyway 做了迁移，迁移里还带了引导逻辑，保证升级后一定有人能进去。
>
> 安全上做了三层：拦截器负责认证、Service 层负责授权、业务层负责合规性校验。授权是每次请求实时查库判断的，不信任前端。
>
> 还加了几条护栏：管理员不能封禁自己、不能撤销最后一个管理员，避免把系统锁死。
>
> 删除功能是最麻烦的，因为用户、工作空间、知识库下面挂着一堆子表，直接删会撞外键约束报 1451。我按子表依赖的深度排序，从叶子往根删，把最深两层的删除逻辑抽成公用方法。这个顺序是硬性的，换一下就会报错。"

## 八、常见问题

**Q：为什么 V7 迁移里要有引导逻辑？**
A：如果只是加个字段，所有人 `is_admin` 默认都是 `FALSE`——系统立刻就没人能进后台了。引导逻辑保证升级后至少有一个管理员，这是**生产环境迁移必须考虑的问题**。

**Q：删除用户和封禁用户有什么区别？**
A：封禁是改状态，数据全在，随时能解封，**可逆**；删除是物理清除，连带名下所有数据，**不可逆**。所以 UI 上删除有二次确认且明确告知会连带删掉多少东西。

**Q：管理员自己能看到后台入口吗？**
A：入口由前端的 `isAdmin` computed 控制显隐（`v-if="isAdmin"`）。但这只是**体验优化**——就算有人手动输入 `/admin` 地址，后端那三层校验一样会挡住他。前端隐藏永远不是安全措施。

**Q：普通登录和管理员登录，登录后拿到的 token 有区别吗？**
A：**没有区别**。token 是同一个东西，权限判定不靠 token 类型，而是每次请求时查数据库里这个用户的 `is_admin` 值。这样做的好处是：撤销某人管理员权限后，他手里已有的 token 立刻失效了后台访问权——如果权限烧进 token 里，就得等 token 过期才生效。

## 九、部署说明（重要）

本项目**常规**部署方式是重建镜像：

```bash
docker compose -f deploy/docker-compose.yml build backend frontend
docker compose -f deploy/docker-compose.yml up -d backend frontend
```

但 `backend` / `frontend` 的 Dockerfile 都依赖从 Docker Hub 拉取基础镜像（`maven:3.9.11-eclipse-temurin-21`、`eclipse-temurin:21-jre`、`nginx:1.29-alpine`）。**如果 registry 不可达，build 会失败**（`failed to resolve source metadata ... EOF`）。

此时可用的替代方案是**直接把产物复制进运行中的容器**：

```bash
# 后端：先打包，再复制 jar 进去，然后重启容器
mvn -o package -DskipTests
docker cp backend/target/ai-knowledge-copilot-0.0.1-SNAPSHOT.jar ai-copilot-backend:/app/app.jar
docker restart ai-copilot-backend

# 前端：dist 复制进 nginx 静态目录，无需重启
docker cp frontend/dist/. ai-copilot-frontend:/usr/share/nginx/html/
```

原理：**容器重启（`restart`）不会重置文件系统，只有重建容器（`--force-recreate`）才会从镜像恢复。**

> ⚠️ **这条要记住**：用 `docker cp` 部署的改动是"临时"的。一旦执行
> `docker compose up -d --force-recreate`，容器会从**旧镜像**重新创建，
> 本次改动**全部丢失**。
>
> 所以等 Docker Hub 网络恢复后，务必**补一次正式的镜像重建**，把改动固化进镜像。
