## 叙事一：检索质量是「测」出来的，不是「感觉」出来的

**背景**：RAG 系统最大的风险是「看起来能答」——没有评估集，任何检索改动都是玄学。

**做法**（三步，每步都有一次自我纠错）：

1. **先建评估集，再谈优化**。10 篇 Markdown 语料切成 44 个 chunk，28 道题按 chunk 级判分（`Recall@5` 看捞不捞得到，`MRR`/`Hit@1` 看排得够不够前）。
2. **评估集本身也要被审查**。第一版按「命中哪篇文档」判分——每篇只有 1 个 chunk，三种检索全 100%，**测不出任何差异**。改成 chunk 级 + 长目录型语料后差异才显现（纯向量从虚高的 100% 掉到真实的 60.7%）。第二版判分串只认编号又虚高——一篇罗列型号的目录片段也含 `2500`。修正后关键词从 92.9% 降到 89.3%：**下降的不是系统，是虚高被挤掉了**。
3. **数据驱动的切片升级**。把「纯文本等距切」改成「结构感知切」：每个 chunk 前面拼上它的标题链前缀（`索引基础概念 > 覆盖索引`）。纯向量 Hit@1 60.7% → 78.6%，语义题 87.5% → 100%，而混合检索保持 100% 零退化。代价几乎为零——每片多几十个字符。

**结果**：混合检索（向量 + BM25，RRF 融合）+ 标识符加法提权，28 题 Hit@1 100%。

**加分细节——重排器事故**：我按常识加过一个基于词覆盖率的重排器，实测 Hit@1 反而从 92.9% 掉到 89.3%。逐段拆解定位到两个 bug：标识符分词不匹配（查询写 `V8`、文档写 `V8__add_source_retriever`）+ 中文 bigram 跨词噪声。修复时的关键判断：**一个能推翻融合结果的弱重排器，比没有重排更糟**——本地重排器不是 Cross-Encoder，判别力不够，不该拥有「推翻」的权限。所以从「全局重排」改成「加法提权」：查询没有标识符时加成恒为 0，排序完全等于融合结果，**结构上不可能退化**；有标识符时只抬名次、其余 23 题零退化。

**续集——真 Cross-Encoder 也不拿绝对推翻权（阶段八）**：换说法题集上 hybrid Hit@1 只有 41.7% 而 Recall@5 有 91.7%——正确片段都捞到了、只是排不对，这正是精排的定义域。接 gte-rerank-v2 后该集 Hit@1 到 66.7%（+25pp），**但主评估集从 100% 回归到 92.9%**：`ERROR 1215` 这种标识符精确命中的题被语义分压到第三。修法不是调参而是改权力结构：`最终分 = CE 分 + 标识符加成`，口语化查询加成为 0（那 +25pp 逐题保持），含编号查询由精确命中守住。一句话总结这条演进线：**弱信号不配推翻权 → 强信号也不该有绝对推翻权 → 每个信号只加在自己确证的范围里**。默认开关等主集复测数字（DashScope 欠费中断了评估），规矩和查询改写一致：没有数字不开默认。

**追问「查询改写为什么默认关」**：在 28 题上改写档与 hybrid 同为 100%——天花板到了测不出提升。新造的 12 道换说法题集上，改写把 Recall@5 从 91.7% 提到 100%（跑两次都复现），但 MRR/Hit@1 的「提升」两次结果一个 58.3% 一个 33.3%，判定为单次抽样运气。**不可复现的收益不能当作开启一项默认配置的理由**，何况它每题多一次模型调用。`app/settings.py` 默认 `query_rewrite_enabled=false`，报告 12.7 节留了完整论证。

## 叙事二：Token 有效 ≠ 账号有效（认证与授权）

**缺陷**（实测复现后修复，`docs/架构审查报告.md` BUG-1）：封禁用户后，旧 token 还能用最长 8 小时。根因是认证只查 Redis 的 `token → userId` 映射，**「token 有效」被等同于「账号有效」**——但账号可能已被封禁。

**修复**：token 验证通过后回查一次数据库，账号非 ACTIVE 立即 401。实测：封禁后同一旧 token 从 200 变 401，且未误伤正常用户。

**面试点**：这是「认证」与「授权状态」分离的经典陷阱。Token 解决「你是谁」，「你现在还能不能进来」必须查权威数据源。代价是每请求一次主键查询，换来权限变更**立即生效**。

**同层的其他设计**（每个都能展开 2 分钟）：
- **授权 fail-closed**：工作空间/知识库/会话三层全部校验成员关系，缺省拒绝；OWNER 收紧为唯一可管理空间的角色。
- **限流在鉴权之后、业务之前**：所有触发模型调用的端点共用同一 Redis 配额。验证方式很省钱——故意打一个无权会话，状态码序列是「20 次 403 然后 429」，证明扣配额发生在鉴权后、模型调用前，全程不花钱。
- **内部服务鉴权**：ai-service 曾在 compose 网络内裸奔（任何容器可直调删除索引）。加共享 `AI_SERVICE_INTERNAL_TOKEN`，FastAPI 中间件用 `hmac.compare_digest` 校验，健康检查豁免。

## 叙事三：级联删除要问「还有谁的外键指向我」

**缺陷**（`架构审查报告.md` BUG-2）：删除用户时只删**他自己**的会话。但协作场景下，其他成员会话可能挂在他拥有的知识库下——外键约束导致整批删除回滚、删除用户 500。为什么原来没暴露？测试环境全是单成员工作空间。**这是一颗多人协作一上线就炸的定时炸弹**。

**修复**：删资源前，先删所有指向它的记录——**不管记录属于谁**。按「归属人」删和按「被引用资源」删是两个维度，漏了后者必然翻车。

**同类问题**（本轮主动排查）：删除知识库/文档只清了 MySQL 和 MinIO，**Milvus 向量残留**——重新上传同名文档会检索到旧内容。修复：ai-service 新增幂等的索引清理端点，删除流程先清向量再删元数据。跨存储系统的一致性（MySQL/MinIO/Milvus 三处）靠「先清下游、再删上游」的顺序保证。

## 叙事四：前端竞态治理 —— 单调 requestId + 身份捕获

**问题**：快速切会话/知识库/工作空间时，先发出的慢请求后返回，会覆盖新状态（旧会话的消息闪现在新会话里）。

**方案**（全项目统一的模式）：
- 每类请求一个单调递增序号，响应回来序号对不上就丢弃；
- 更强的一致性场景捕获「身份三元组」（如发消息时的 sessionId + knowledgeBaseId），执行完成后逐项比对——中途切走的结果属于上一屏，写进来会串台；
- SSE 流用 AbortController，且以**控制器身份**判断归属（切走触发的 abort 不等于失败）；组件卸载统一作废。

**验证**：`workspace.spec.ts` 里有一条专门的用例——切换会话后派发上一条生成流的迟到 delta，断言不渲染、且请求确实被 abort。

**收敛**（能体现重构能力）：7 个视图曾各自复制这套样板，收敛为两个组合式函数——`useWorkspaceContext`（模块级单例：登录态/工作空间/知识库列表全局一份）和 `useChatSessions`（会话列表的翻页去重、过期丢弃、刷新保序，Chat 与 Agent 两页共用一份实现）。共享逻辑新增 21 个用例钉住。

## 叙事五：不用 Spring AI 的模型调用层（高频追问）

**为什么不用 Spring AI / LangChain？**

架构上，Java 层**一行模型代码都没有**。Spring Boot 通过 `HttpURLConnection` 调自研 ai-service（FastAPI），真正的模型调用在 Python 侧（`answering.py`）。组织方式：**一个能力 = 一个函数式接口 + 一个 lambda `@Bean`**，6 个全在 `AiServiceConfiguration.java`，每个 Bean 第一件事都是降级开关判断。

话术要点：**Spring AI 解决的是「Java 直接调模型」；本项目是「Java 调自研 AI 服务」，中间隔了一层——语言边界就是服务边界。** 收益：AI 逻辑（切片、检索、重排、Agent 循环）独立于 Java 发布节奏；Embedding/Milvus 的 Python 生态直接可用；backend 保持纯业务编排。

**Agent 的 Tool Calling**：三个工具（`knowledge_search` / `list_documents` / `document_outline`），关键约束：
- 工具**只访问服务端注入的知识库 id**，模型无权指定——权限边界不交给模型；
- 工具**不抛异常**，失败收敛为四态 `ToolStatus`（`ok/empty/not_found/error`）——「没查到」和「工具坏了」对模型是两种处置方式；
- 只有 `knowledge_search` 的返回进 `sources`，防止把文档清单误列成引用；
- 工具轮数用尽后必须再发一次**不带工具**的请求，否则已取回的证据全被丢掉。

## 高频追问速答

| 问 | 答（事实依据） |
|---|---|
| 为什么混合检索？ | 纯向量对编号/型号/错误码这类字符串天然盲（`ERROR 1451` 的向量会退化成「数据库报错」泛化语义），Hit@1 只有 70%；BM25 靠字面精确匹配补上；RRF 融合后两组都 100% |
| Milvus 怎么用？ | Inner Product + `text-embedding-v4`（1024 维）；collection 只有 5 个字段；**过滤条件下推到召回内部**（表达式过滤），不取回后再筛 |
| 切片怎么切？ | 结构感知：标题链前缀打进 chunk 正文 + 完整语义单元；配置集中在 `settings.py` |
| SSE 遇到什么坑？ | Nginx 代理缓冲会把流聚合成一次性返回，需显式关闭；停止生成 = 客户端 abort + 后端不写入残缺回答 |
| 解析任务怎么做可靠？ | 任务状态机 `ACCEPTED→PROCESSING→COMPLETED/RETRYING/FAILED`；MySQL 条件 UPDATE 乐观抢占；启动恢复 + 指数退避重试；重启后自动恢复未完成任务 |
| 怎么测的？ | 四层：后端 121（服务层单测）· 前端 83（vitest + vue-tsc）· ai-service 220（pytest）· GitHub Actions CI 自动跑三层测试 + compose e2e（已全绿），部署后再跑 HTTP 全链路脚本 |
| DOCX 表格丢失怎么修的？ | python-docx 默认只遍历段落；改用 `iter_inner_content()` 按文档序交错遍历段落与表格，表格行转 `列名: 值` 文本进切片 |
| 印象最深的 bug？ | 备选：封禁后 token 仍有效（认证≠授权状态）；重排器把 92.9% 降到 89.3%（弱重排器不该有推翻权）；评估集虚高 100%（判分口径错误会直接变成错误的工程结论）；**MinIO 官方撤源**（Docker Hub 删库/quay 401/dl.min.io 410，本地旧镜像层掩盖了「全新环境必挂」，最终从 GitHub Releases 自建镜像消掉第三方依赖） |
| 线上怎么观测？ | `/actuator/prometheus`（仅 compose 内网可达）：`aicopilot_ai_request_seconds{capability,outcome}` 看每个 AI 能力的 P95 与失败率，`aicopilot_ratelimit_rejected{bucket}` 看限流拒绝；ai-service 解析按阶段打耗时日志（下载/切片/索引） |
