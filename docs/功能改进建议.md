# 功能现状盘点与改进建议（对标 GitHub 同类项目）

> 调研日期：2026-09-18
> 对标对象：**RAGFlow**（~90k stars，深度文档理解 + 混合检索）、**Dify**（~117k stars，LLM 应用开发平台）
> 方法：本地代码全量盘点 + 同类项目特性调研 → 差距分析 → 分优先级建议

## 二、三个核心判断（这部分比功能列表更重要）

### 判断 1：不要对标"平台型"产品做功能堆砌

Dify 和 RAGFlow 的本质是**平台**——它们卖的是"让你不用写代码就能搭 AI 应用"，所以可视化工作流编排是它们的核心。

**本项目是垂直应用**（企业知识库问答），不是平台。花大力气做可视化拖拽编排是**方向性错误**——工作量以周计，且做完也讲不出深度。

> 面试时如果被问"为什么不做工作流编排"，正确回答是：
> "我们的定位是开箱即用的企业知识库，不是低代码平台。工作流编排会显著增加使用门槛和维护成本，
> 而这个场景下用户要的是'上传即问'。如果要做多步编排，我更倾向在 Agent 层用代码定义工具链，
> 而不是让用户拖拽。"

### 判断 2：检索质量是唯一必须补的短板

RAG 项目的成败 90% 在检索。现在**纯向量召回**有个致命弱点：**对专有名词、编号、缩写不敏感**。

举例：用户搜 "ERROR 1451" 或 "V7 迁移"，向量可能召回一堆语义相近但**不含这个关键词**的片段；而 BM25 关键词检索能精确命中。

这不是理论问题——企业知识库里恰恰充满了编号、术语、产品名。**纯向量召回在这个场景下会频繁答非所问。**

### 判断 3：深度 > 广度

与其堆 10 个半成品功能，不如把**混合检索做深做透**。

面试时能讲清「BM25 + 向量 + RRF 融合 + Cross-Encoder 重排」这一整套，比讲"我做了知识图谱、多模型接入、文本转 SQL"（都是浅尝辄止）有价值得多。

## 三、改进建议（按优先级）

### P0：强烈建议，投入产出比最高

#### 建议 1：混合检索 + Rerank 🔥

**为什么**：这是 RAG 项目面试必问的"检索质量怎么优化"。现在答不上来，做完能完整讲一套。

**怎么做**（分三步，可以分步落地）：

1. **加关键词通路（BM25）**
   - 最简单的做法：MySQL 建 `knowledge_chunk` 表存切片原文，用全文索引（`MATCH ... AGAINST`）或轻量 BM25 库
   - 或者用 Elasticsearch，但会显著增加部署复杂度，**不建议**（你现在已经有 Milvus + MySQL + Redis + MinIO 四个存储了）

2. **两路召回融合（RRF）**
   ```
   RRF_score(chunk) = Σ  1 / (k + rank_i)
   ```
   `k` 通常取 60。RRF 的好处是**不需要归一化两路的分数**（向量分数和 BM25 分数不可比），鲁棒性好。

3. **Rerank 精排**
   - 用 Cross-Encoder（如 `bge-reranker`）对 top-50 重排，取 top-5
   - 注意：Rerank 是**串行计算**，延迟高，只对少量候选做

**预期收益**：召回准确率显著提升，尤其是对编号/术语类查询。**这是能让项目从"能跑"变成"好用"的关键一步。**

**面试话术**：
> "最初我们只用向量召回，发现对专有名词和编号不敏感——比如搜 ERROR 1451 会召回语义相近但不包含这个错误码的片段。
> 后来改成了混合检索：向量保证语义泛化能力，BM25 保证关键词精确命中，用 RRF 融合避免分数归一化问题，
> 最后用 Cross-Encoder 对 top-50 重排。Rerank 延迟高所以只对少量候选做，不做全量。"

---

#### 建议 2：前端 Markdown 渲染 + 代码高亮

**为什么**：企业知识库的回答经常含代码块、表格、列表。现在是纯文本 `{{ item.content }}`，格式全丢，体验很差。

**怎么做**：加 `markdown-it` + `highlight.js` 两个依赖（`package.json` 现在只有 vue 和 vue-router），在 `ChatView.vue` 渲染消息时用 `v-html`。

**注意**：用 `v-html` 必须做 XSS 防护——要么对模型输出做白名单过滤，要么用 `DOMPurify`。**这点面试会被追问**，别忘了。

**成本**：半天。**体验提升非常明显。**

---

#### 建议 3：加 Swagger / OpenAPI 文档

**为什么**：现在没有任何 API 文档，这在工程化上是个硬伤。而且成本极低。

**怎么做**：`pom.xml` 加 `springdoc-openapi-starter-webmvc-ui` 依赖，访问 `/swagger-ui.html` 即可自动出文档（基于现有 Controller 注解）。

**成本**：不到 1 小时。**性价比最高的一条。**

---

### P1：值得做

#### 建议 4：扩展文档格式（Excel / PPT / HTML）

`processing.py:240-250` 现在只支持 txt/md/csv/pdf/docx。企业场景里 Excel 和 PPT 极其常见。

- Excel：`openpyxl`（按 sheet + 行切片，保留表头）
- PPT：`python-pptx`（按页切片）
- HTML：`beautifulsoup4` 提取正文

**注意**：Excel 的切片策略要特殊处理——不能按字符硬切，否则会把表格切碎。应该**按行切**，且**每行带上表头**，否则模型看不懂单元格含义。这个细节面试能加分。

---

#### 建议 5：改进切片策略（结构感知）

现在 `indexing.py:30-34` 是固定 800 字符滑动窗口。问题是**会把一个完整的段落/表格从中间切断**。

改进方向（从易到难）：
1. **按 Markdown 标题层级切**：识别 `#` `##`，保证一个 slice 不跨标题
2. **保留上下文前缀**：每个 chunk 带上它所属的小标题，例如 `"## 退款政策 > 超过5万元的审批流程：..."`
3. 语义切片（按句子 embedding 相似度聚类）—— 成本较高，可选

第 2 条成本很低但效果显著，**优先做**。

---

#### 建议 6：给 Agent 加 2-3 个工具

现在只有 `knowledge_search` 一个工具。可以加：
- 文档列表（"这个知识库有哪些文档"）
- 按文档过滤检索（缩小范围）
- 时间范围过滤

**成本**：每个工具就是一个 Python 函数 + JSON Schema 描述，不难。

**价值**：能讲清 Tool Calling 的设计——工具描述怎么写、模型怎么选工具、结果怎么回灌。

---

#### 建议 7：RAG 效果评估

做一个小评估集：20-30 条「问题 → 期望命中的文档」，测 Recall@5 / MRR。

**面试价值很高**——大部分候选人只会说"效果还行"，能拿出量化指标的是少数。

## 四、不建议做的（避免走偏）

| 不做 | 原因 |
|---|---|
| **可视化工作流编排** | 这是 Dify 的核心卖点，但本项目是垂直应用。工作量以周计，做完也讲不出深度，还会把架构搞复杂 |
| **知识图谱** | RAGFlow 有，但收益不明确、成本高。对面试而言，讲"我评估过知识图谱但选择了混合检索"比"我做了个半成品知识图谱"更有说服力 |
| **文本转 SQL** | 偏离"知识库问答"主线 |
| **盲目加存储组件** | 已经有 MySQL + Redis + MinIO + Milvus 四个了。加 Elasticsearch 要慎重——**用 MySQL 全文索引做 BM25 就够了**，别为了"技术栈好看"引入运维负担 |

## 五、建议路线图

如果要按优先级推进，我建议这个顺序：

```
第 1 周：Swagger + Markdown 渲染        （成本低，立刻见效）
第 2-3 周：混合检索（BM25 + RRF）        （核心价值，重点投入）
第 4 周：Rerank + 效果评估集             （把检索质量闭环）
第 5 周：Excel/PPT 解析 + 切片改进       （补齐企业场景）
之后：Agent 工具扩展、查询改写、限流分页
```

**如果时间只够做一件事**：做**混合检索**。它是唯一能同时提升"实际效果"和"面试深度"的改动。

**阶段二 + 五 的量化结果**（28 题，chunk 级双条件判分，详见 `docs/检索效果评估报告.md`）：

| 配置 | MRR | Hit@1 |
| --- | ---: | ---: |
| 纯向量 | 78.6% | 60.7% |
| 纯关键词（BM25） | 94.0% | 89.3% |
| 混合 · 仅 RRF 融合 | 96.4% | 92.9% |
| **混合 · RRF + 标识符提权** | **100.0%** | **100.0%** |

> 过程中有一次真实的技术判断失误与纠正：最初按常识加的「IDF 加权词覆盖率」全局重排把 Hit@1 从 92.9% 拉低到 89.3%。教训是——**一个能推翻融合结果的弱重排器，比没有重排更糟**。详见评估报告第六节。

**阶段三 的量化结果**（同一套 28 题、同一套判分口径，语料从 16 个 chunk 重新切成 **44 个 chunk**）：

| 配置 | Recall@5 | MRR | Hit@1 | 阶段三前 Hit@1 |
| --- | ---: | ---: | ---: | ---: |
| 纯向量 | 100.0% | 87.6% | 78.6% | 60.7% |
| 纯关键词（BM25） | 100.0% | 91.7% | 85.7% | 89.3% |
| **混合检索** | **100.0%** | **100.0%** | **100.0%** | 100.0% |

切片改进对**纯向量**的提升最明显（Hit@1 **60.7% → 78.6%**）：每个 chunk 从「几百字的无主题窗口」变成「一个完整小节 + 所属标题链前缀」，向量终于带上了主题信息。混合检索保持满分且**全部 28 题都排第一**。纯关键词小幅回落 3.6pp（恰好等于 1 道题），是切片变细后候选更密集所致，在 28 题规模下属于噪声范围。

**阶段四 的成果**：工具从 1 个扩到 3 个，测试从 123 个增到 **161 个**（全通过），并新增两个冒烟脚本。

| 新增文件 | 作用 |
|---|---|
| `ai-service/app/agent_tools.py` | 工具定义 + JSON Schema 说明书 + 统一的参数收敛与错误收敛 |
| `ai-service/scripts/smoke_agent.py` | 容器内直调三个工具 + 跑完整问答（只读，可随时重跑） |
| `scripts/e2e_agent.py` | 走 HTTP 打后端的端到端验证（注册 → 建库 → 上传 → 解析 → 问答 → 落库） |

这一阶段最有价值的部分**不是写出了工具，而是端到端测试逼出来的三个设计缺陷** —— 它们单靠单元测试发现不了，因为都出在「模型的行为」与「我们这侧的实现」的交界处：

1. **模型把文件名当成 `document` 传。** `list_documents` 显示的是文件名（`inspection-robot.md`），真正的取值是 object_key（`kb/32/<uuid>/inspection-robot.md`）。模型看到什么就传什么，于是过滤条件无效。
   **修复**：`knowledge_search` 原本对「过滤后为空」静默返回空列表 —— 但空结果有两种病因（参数错了 / 文档里确实没有），对模型的处理方式完全相反。现在只有失败路径上才多做一次清单核对，并在参数无效时把**正确的取值直接列给模型**。修复后同一道题的调用数从 4 次降到 2 次，且第一次失败就能自纠。

2. **轮数用尽时把已取回的证据全丢掉了。** 模型是很爱探索的，一次提问连发四个工具调用很常见，`agent_max_rounds=3` 被烧光后代码直接返回一句「达到最大工具调用次数」—— 而对话里已经攒着 4 条命中的片段，它本来完全答得出来。
   **修复**：预算用尽后再发一次**不带工具**的请求。这比单纯把轮数调大更好：调大只是把问题推后，探索型模型照样能烧完；不带工具的这一轮是**结构性保证** —— 它只有「用现有资料作答」这一条路。

3. **导航类工具的结果不能算引用来源。** 文档清单和目录是「导航信息」，并进 `sources` 会让前端把一份跟问题无关的清单列成引用来源。
   **修复**：只有 `knowledge_search` 返回的片段才进 `sources`。实测中「知识库有哪些文档」这道题的 `source_count` 为 0、回答正确 —— 契约成立。

另外两处工程细节：

- **越权防线**：`object_key` 是共享对象存储里的路径，模型完全可以编造出 `kb/9/.../secret.md`。`document_outline` 会先核对这份文档确实属于当前知识库，再决定要不要把内容读出来。而 `knowledge_search` 不需要这道检查 —— 它的过滤条件是拼进 Milvus 表达式的，表达式里带了 `knowledge_base_id`，数据边界本身就保证了安全。**同一个安全目标，两条成本不同的实现路径**，这点在面试里很好讲。
- **参数校验不能指望 JSON Schema**：Schema 里的 `minimum` / `maximum` 只是给模型看的提示，不是强制校验。工具侧必须自己兜住 `limit=100000` 这种输入。

**已知的一处展示瑕疵**（阶段六已修）：前端执行轨迹面板固定渲染 `{{ step.resultCount }} chunks`，而 `list_documents` 与 `document_outline` 返回的单位是「篇」和「小节」，于是会显示成「列出知识库中的全部文档 · 10 chunks」。

**阶段六 A 组「修硬伤」的成果**（三处阻碍部署演示的缺陷）：

| # | 硬伤 | 真实成因 | 修法 |
|---|---|---|---|
| 1 | 非 local 环境后端 404 | 24 个类打了 `@Profile("local")`，**且** datasource / redis / storage / ai-service 配置全在 `application-local.yml` 里。不激活 local 时这些 Bean 根本不存在，容器甚至起不来 | 删掉 24 个 `@Profile("local")` + 把 `application-local.yml` 合并进 `application.yml` + 删掉 compose 里的 `SPRING_PROFILES_ACTIVE: local` |
| 2 | 大文档被重复解析、白烧 embedding | `task_processing_stale_seconds=300` 小于大文档解析耗时；而解析期间**一次 UPDATE 都没有**，所以 `updated_at` 不会前进 → 恢复循环把它判成僵尸任务，从头再做一遍（重新下载 / 切片 / embedding） | 处理期间加**心跳线程**持续刷新 `updated_at`；并把 `claim` 改成显式 `SET updated_at = NOW()` |
| 3 | 执行轨迹单位词错配 | 面板是只有 `knowledge_search` 时写的，「query」「chunks」当时都对；加了两个导航工具后不再成立 | 按 `step.tool` 切换量词（片 / 篇 / 小节），并去掉误导性的 `query · ` 前缀 |

**硬伤 1 的复现证据**：把旧 jar 放进一个没有 `SPRING_PROFILES_ACTIVE` 的容器，Spring Boot 直接 `APPLICATION FAILED TO START`：

```
Description:
...
Reason: Failed to determine a suitable driver class
Action:
...
	If you have database settings to be loaded from a particular profile you may need to activate it
	(no profiles are currently active).
```

官方给出的 Action 恰好指向根因 —— 配置被锁在 profile 文件里。这也说明「'local' 这个 profile 名字本身就是错的」：它装的全是生产必需的 Bean，它不是「本地用」，而是「这个应用的全部功能」。

修复后同一容器在无 profile 状态下 `running|healthy`，`/api/v1/health` 返回 200，端到端链路正常。

**顺带修好的两个测试**：去掉 `@Profile` 之后，两个原本「靠 Bean 根本不存在」侥幸通过的上下文测试暴露了出来 —— `ApplicationTest`（`spring.autoconfigure.exclude` 排掉了 `DataSourceAutoConfiguration`，于是新出现的 `Jdbc*Repository` 找不到 `JdbcTemplate`）和 `HealthControllerTest`（`@WebMvcTest` 切片会把 `WebMvcConfigurer` 一起装配，`AuthenticationWebConfiguration` 需要 `AuthenticationInterceptor`，而拦截器背后是 MySQL + Redis）。
修法是让这两个测试各自补上缺失的那一块：前者只排除 Flyway（Hikari 在首次 `getConnection()` 前不建物理连接，Context 能照常启动），后者用 `@MockitoBean` 给拦截器一个替身。**它们此前一直没有真正验证过完整装配**，现在才是真的冒烟测试。

**测试基线**：后端 36 个用例（11 个测试类，`mvn -o test` 全通过）；ai-service 161 → **172** 个用例（新增 11 个心跳与任务存储的用例）。

**阶段六 C 组「工程化补齐」的成果**（限流 / 分页 / 前端测试框架 / 多标签页状态同步）：

| # | 项 | 之前 | 现在 |
|---|---|---|---|
| 1 | **限流** | 完全没有。`POST /users/login` 可以无限次试密码；`ask` / `ask-agent` / `stream` 三个走 LLM 的接口可以无限刷 | 新增 `RateLimiter` + `RateLimitProperties`，登录失败 5 次 / 15 分钟锁定，LLM 接口 20 次 / 分钟。超限返回 **429 `RATE_LIMIT_EXCEEDED`** |
| 2 | **分页** | 全仓库没有任何 `LIMIT`/`OFFSET`（grep `LIMIT` 只命中概览的三处 `LIMIT 5`）。会话和消息列表随使用无界增长 | 新增 `PageQuery` / `PageResponse` 通用分页；会话列表与消息列表改为 `{items, page, size, totalElements, totalPages, hasNext}`，前端加「加载更多 / 加载更早的消息」 |
| 3 | **前端测试** | 一个测试都没有，`package.json` 里没有 test 脚本 | 引入 vitest 3 + `@vue/test-utils` + jsdom，**33 个用例**（跨标签同步 / Markdown XSS 防线 / 分页契约） |
| 4 | **多标签页状态** | A 标签登出后 B 标签仍显示已登录（详见下文根因） | 新增 `crossTabSync.ts` 监听 `storage` 事件并翻译成本项目已有的自定义事件，**所有既有监听者零改动受益** |

**第 4 项的根因值得单独记一笔**，因为它是一个「两边各缺一块、拼起来正好漏掉」的典型：

- `localStorage` 是跨标签页共享的，但 `storage` 事件**只派发给「其它」标签页** —— 写的那一方自己收不到；
- 而项目里现有的 `aicopilot-auth-changed` / `aicopilot-workspace-changed` 是自定义事件，`dispatchEvent` **只在本标签页内传播**。

于是：A 标签登出 → 清 localStorage + 派发自定义事件 → A 自己刷新正常；B 标签既没监听 `storage` 事件、又收不到自定义事件 → 仍然显示已登录，直到用户手动刷新。修法是在中间**架一座桥**（监听 `storage` → 翻译成自定义事件），而不是去改那 5 个监听者。

**第 2 项顺带修掉了一个成本问题**：改造前 `ask` / `askAgent` / `streamAsk` 都把**整个会话的全部消息**作为历史送给模型，一个聊到 200 轮的会话每次提问都要重新计费 400 条消息（越聊越贵、越聊越慢）。现在统一走 `findMessages(sessionId, 20, 0)` ——「从最新往回取 20 条」，界面翻页和上下文窗口用的是同一个查询，只是 offset 不同。

**分页实现里两个容易踩的坑（面试可讲）**：

1. **`LIMIT` 作用在行上，不是消息上。** 原来的 `findMessages` 用 `LEFT JOIN conversation_message_source` 一次查出来再在 Java 里分组 —— 一条消息有 N 个来源就展开成 N 行，加了 `LIMIT 20` 之后实际可能只取到 3 条消息。改成**两步查**：先取消息主体（`LIMIT` 作用在 `conversation_message` 上），再按这批 id 批量补来源与执行轨迹。
2. **`?size=1000000` 能一边用一个 query string 把分页打成 DoS。** `PageQuery` 在**一个地方**统一收敛：不传给默认值、负数归零、超大值压到上限 100。上限存在的意义不是「限制用户」，而是「让外部可控的返回数据量有界」。同时 `offset()` 返回 `long`（`page * size` 用 int 会溢出成负数，传给 SQL 直接报错）。

**验证方式**：新增 `scripts/verify_c_group.py`，在真实容器上做 33 项端点级断言（分页外壳字段、参数归一化、越界页 `hasNext=false`、登录 429 的触发点、以及「LLM 接口的配额是在鉴权之后、业务逻辑之前扣除」）。**测试基线**：后端 36 → **74** 个用例、前端 **33** 个用例、ai-service 172 个用例，全通过。

**阶段六 B 组「查询改写 + 新格式纳入评估集」的成果**：

| # | 项 | 结果 |
|---|---|---|
| 1 | **查询改写（Multi-Query）** | `app/query_rewrite.py`（LLM 改写，**任何失败都返回空列表 = 退回单查询**）+ `hybrid_search.multi_query_retrieve`（对原问题与各条改写各跑一遍完整检索，再用 RRF 融合，最后**用原问题重排**）。功能完整、有 28 个单测 |
| 2 | **默认是否开启** | ❌ **不开启**。依据是实测：稳定提升的只有 Recall@5（91.7% → 100%），排序指标两次运行一次比 baseline 好、一次更差；代价是每次提问多一次模型调用。详见 `docs/检索效果评估报告.md` 第十二节 |
| 3 | **新格式纳入评估集** | 新增 4 份语料（xlsx / pptx / csv / html）+ 13 道题，**全部被四档模式召回**，证明「解析 → 结构化切片 → 入库 → 检索」整条链路打通 |
| 4 | **新工具** | `docs/rag-eval/build_new_format_corpus.py`（标准库手写 OOXML 生成语料 + 真实解析器自检）、`ai-service/scripts/verify_question_spans.py`（**离线**核对判分串，写题时就能用） |

**这次最有价值的产出不是功能，而是两条方法论**：

1. **一个功能，不能在一个「它不可能失败」的题集上被验证。** 查询改写跑现有 28 题的结果是「变好 0 / 变差 0 / 不变 28」——不是它没用，而是**那批题的措辞是从语料里抄的**，混合检索已经 100% Hit@1，天花板到了。于是另做一套「口语化提问」题集（语料、口径、库都不变，**只改提问措辞**并刻意避开所有语料术语），才测出真实差异。
2. **不可复现的机制必须跑两次。** 改写按温度 0.8 生成，两次跑出 Hit@1 58.3% / 33.3%（baseline 恒为 41.7%）。前三个模式两轮**逐题完全一致**，正好证明波动只来自改写。于是能把「稳定的收益（召回）」和「不稳定的收益（排序）」分开，而不是把一次抽样的运气写成结论。

**顺带发现**：在只有 **10 个 chunk** 的小语料上，混合检索（Hit@1 92.3%）**反而不如纯向量或纯 BM25（都 100%）**——融合的价值来自两路互补，语料小且内容彼此不同时，它只是在给本来就正确的排序引入扰动。这跟第六节「弱重排器比没有重排更糟」是同一类现象，也说明**评估结论必须带上语料规模**。

## 六、一条容易被忽略的建议：先解决"能不能演示"

> **✅ 阶段六 A 组已解决**（详见第五节末尾）。下面保留原始分析，作为这个问题价值的记录。

有个现实问题：**`@Profile("local")` 导致非 local 环境下所有后端 Bean 不加载**。

本地开发没问题（docker-compose 里配了 `SPRING_PROFILES_ACTIVE=local`），但如果你想**部署到服务器给面试官看**，会直接 404。

如果要做公开演示，需要：
- 要么把 profile 改成默认激活
- 要么部署时显式指定 `SPRING_PROFILES_ACTIVE=local`

**另外**：Docker Hub 目前连不上，`docker compose build` 会失败，改动是用 `docker cp` 临时部署的——**`--force-recreate` 会丢失所有改动**。正式演示前务必补一次镜像构建并验证。

> 注意：修复后这一条的风险变了。`SPRING_PROFILES_ACTIVE` 已经不需要了，但 **`docker cp` 的临时性没变** —— 容器重建（`docker compose up --no-build` 或 `--force-recreate`）会退回镜像里的旧 jar，必须补一次正式构建。本次复验时正是因为先 `docker compose up -d --no-build backend` 重建了容器，才额外抓到了旧 jar 的启动失败证据。
