# 数据库索引与慢查询调优

## 为什么需要调优

数据库性能问题绝大多数来源于不合理的索引设计和低效的 SQL 写法。当单表数据量增长到
百万级之后，全表扫描的代价会急剧上升，接口响应时间从毫秒级恶化到秒级。

## 索引设计原则

联合索引遵循最左前缀原则，把区分度高、且查询条件中最常出现的列放在前面。
范围查询之后的列无法继续利用索引，因此范围条件应尽量后置。
选择性极低的列（例如性别、状态标志）单独建立索引收益很小。

## 慢查询定位

开启慢查询日志，用执行计划分析工具查看是否走索引、扫描行数是否接近全表。
出现回表次数过多时，可以考虑覆盖索引，把查询需要的列一并放进索引里。

## 连接池与并发

连接池过小会让请求排队等待，过大会把数据库压垮。一般按并发数乘以单次查询耗时估算，
再留出一定余量。事务中不要长时间持有连接，尤其要避免把外部网络调用放进事务边界内。

## 表结构演进

大表加字段需要评估锁表时间。线上变更应当拆成小步骤，先加可空列、再回填数据、
最后补上约束，避免一次性长事务阻塞写入。
