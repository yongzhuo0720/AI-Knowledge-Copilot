# 版本发布流程规范

## 版本节奏

团队按固定节奏发布版本，每个版本包含若干需求与缺陷修复。版本号由发布负责人统一分配，
不允许各业务方自行跳号。本文描述的是流程本身，具体每个版本改了什么请查阅对应的发布说明。

## 发布前检查

需求验收完成、测试用例执行完毕、性能压测没有明显退化，是发布的三个前提。
数据库结构变更需要额外确认脚本已经过评审，并且在预发环境完整跑过一遍。
涉及配置项调整的，必须同步更新部署文档。

## 数据库变更约定

所有结构变更都以脚本形式管理，脚本集中存放，由服务启动时自动按顺序执行。
已经上线执行过的脚本不再修改，需要调整就追加一个新脚本。
破坏性变更要拆成多个版本逐步推进，先兼容旧结构，再切换读写，最后清理。

## 发布执行

发布窗口一般安排在业务低峰期。执行顺序是先变更数据库、再发后端、最后发前端，
每一步之间留出观察时间。观察期内重点关注错误率、响应时间和关键业务指标。

## 回滚

出现无法快速修复的问题时优先回滚，不在线上排查。回滚前确认本次变更是否包含
不可逆的数据结构修改，如果有，回滚方案需要单独准备。回滚后必须复盘原因，
并把遗漏的检查项补进发布清单。
