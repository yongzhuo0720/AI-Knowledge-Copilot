# 检索效果评估报告

> 评估对象：`ai-service` 的检索模块（`app/hybrid_search.py`）
> 评估集：28 题（20 题含编号/型号 + 8 题纯语义），10 篇语料切出 **44 个 chunk**
> 切片方式：结构感知切片（每个 chunk = 一个完整小节 + 所属标题链前缀），详见第十一节
> 判分粒度：chunk 级 · 双条件
> 复现方式：见文末

---

## 一、结论

一句话：**混合检索（向量 + BM25 → RRF 融合 → 标识符提权）在两组不同类型的查询上都拿到了满分，而单路检索必然在其中一组上明显掉分。**

| 配置 | Recall@5 | MRR | Hit@1 |
| --- | ---: | ---: | ---: |
| 纯向量 | 100.0% | 87.6% | 78.6% |
| 纯关键词（BM25） | 100.0% | 91.7% | 85.7% |
| **混合检索** | **100.0%** | **100.0%** | **100.0%** |

指标口径：`Recall@5` 看捞不捞得到，`MRR` 和 `Hit@1` 看排得够不够前。三者都是 **chunk 级**判分。

**混合检索在全部 28 道题上都把正确片段排在了第一位**，脚本末尾的诊断段输出「hybrid 在全部题目上都排到了第一位」，即零 MISS、零排序退化。

> 这是**切片升级后**的结果。切片从「纯文本等距切」改成「结构感知切」之后，纯向量的 Hit@1 从 60.7% 提到 78.6%（见第十一节）。两套结果的对比与原因分析在该节。

---

## 二、为什么要做量化评估

「混合检索比纯向量好」如果只是主观感觉，那它不是工程结论。只有把同一批问题在三种模式下各跑一遍、给出对比数字，才能：

1. 证明改动确实有效，而不是自我感觉良好；
2. 在下次调整 BM25 参数、候选池大小、提权权重时，判断是**变好还是变坏**。

没有量化指标的调优只能算碰运气。这一点在本次排错中体现得非常直接：**改动方向看起来完全合理，实测却是退化的**（见第五节）。

---

## 三、评估方法

### 3.1 语料

10 篇 Markdown 文档上传到同一个知识库（KB=31），在默认切片参数（size 800 / overlap 120）下切成 **44 个 chunk**：

| 语料 | 字节数 | chunk 数 | 作用 |
| --- | ---: | ---: | --- |
| `db-error-code-catalog.md` | 5725 | 3 | 50 个 MySQL 错误码，每个一级小节约 800 字符 |
| `gateway-model-catalog.md` | 3920 | 2 | 20 个网关型号 |
| `release-history.md` | 2002 | 1 | V1–V18 发布史 |
| `db-tuning.md` | 1300 | 5 | 干扰项：讲同一主题但不含具体编号 |
| `index-basics.md` | 1773 | 7 | 干扰项；也是「覆盖索引」题的答案来源 |
| `db-errors-general.md` | 1621 | 5 | 通用错误处理流程 |
| `hybrid-retrieval.md` | 1540 | 5 | 语义型问题的答案来源 |
| `retrieval-overview.md` | 1694 | 5 | 语义型问题的答案来源 |
| `release-process.md` | 1450 | 5 | 语义型问题的答案来源 |
| `gateway-overview.md` | 1678 | 6 | 语义型问题的答案来源 |
| **合计** | **22703** | **44** | |

注意 chunk 数**不随字节数单调变化**：`release-history.md`（2002 字节）只有 1 片，而 `index-basics.md`（1773 字节）有 7 片。原因正是结构感知切片的行为——后者有 7 个 `##` 小节，标题是**硬边界**，每个小节至少成一片；前者整篇不到 800 字符，即使有多个标题也会被**打包**进同一片（打包时标题前缀会换成最后一段所属的标题链）。这说明切片结果由**文档结构**决定，而不是由长度决定。

**为什么要造「长目录型」语料**：第一版评估集每篇文档只有 1 个 chunk，检索退化成了「选文档」——只要命中那篇文档就必然命中答案，所有模式都能拿 100%，测不出任何差异。改成一篇文档切成多块之后，问题才变成真正的「在多块高度相似的片段里挑对那一块」。

### 3.2 判分粒度：chunk 级，不是文档级

每条问题给出一个 `answer_span`，必须出现在正确**片段**里才算命中。

为什么不按「命中了哪篇文档」判分：回答「ERROR 1451 是什么原因」时，把写着 1366 的那一块捞上来，文档是命中的、答案是错的。文档级指标会把这判成成功，完全掩盖问题。

### 3.3 判分条件：编号 + 答案文本，双条件

`answer_span` 支持两种写法：

- **数组 = 全部出现**（同一片段内）。用于精确编号题，例如 `["2500", "每秒两百次"]`。
- **`answer_any` = 任一备选成立**。用于「同一问题在语料里有两个都正确的片段」的情况。

为什么编号之外还要带上答案文本 —— 只认编号会让指标虚高，实测遇到两种情况：

1. 一篇只罗列型号的**目录片段**同样含 `2500`，但它并没有回答「默认限流参数是多少」；
2. 错误码 `1836` 同时出现在**完整条目**和**被切片截断的残句**里。只认编号时「残句」也算命中，等于把「切坏了」误判成「检索对了」。

> 第 2 种情况其实是**切片策略有缺陷的症状**：旧实现按固定字符等距切，必然把条目从中间切断，同一个错误码才会同时出现在两片里。这正是第十一节「结构感知切片」要解决的问题——改完之后，一个条目只会完整地落在一个 chunk 里。评估集在这里起到的作用是**把切片缺陷暴露出来了**，而不是自己去绕开它。

### 3.4 指标定义

- **Recall@5**：top-5 里存在正确片段的比例 —— 衡量召回能力。
- **MRR**：第一个正确片段排名倒数的均值，未召回的题按 0 计入分母 —— 衡量排序能力。
- **Hit@1**：正确片段恰好排在第一位的比例 —— 最贴近用户体验的指标。

只看 Recall 会漏掉排序退化（正确答案从 #1 掉到 #5，Recall 不变但体验已经变差）；只看 MRR 又会漏掉完全没召回的情况。所以三个都要看。

## 四、结果

### 4.1 总体

```
                       vector    keyword     hybrid
Recall@5               100.0%     100.0%     100.0%
MRR                     87.6%      91.7%     100.0%
Hit@1                   78.6%      85.7%     100.0%
```

### 4.2 分组：含编号 / 型号的查询（20 题，向量检索的弱项）

```
                       vector    keyword     hybrid
Recall@5               100.0%     100.0%     100.0%
MRR                     82.7%      90.8%     100.0%
Hit@1                   70.0%      85.0%     100.0%
```

### 4.3 分组：纯语义提问（8 题，向量检索的强项）

```
                       vector    keyword     hybrid
Recall@5               100.0%     100.0%     100.0%
MRR                    100.0%      93.8%     100.0%
Hit@1                  100.0%      87.5%     100.0%
```

### 4.4 修复前后（同口径可比的一对）

| 配置 | Hit@1 | MRR |
| --- | ---: | ---: |
| 混合 · 关掉重排（仅 RRF 融合） | 82.1% | 91.1% |
| 混合 · 打开重排（标识符提权） | **100.0%** | **100.0%** |

5 道题从 #2 提到 #1（`ERROR 1205`、`ERROR 1071`、`XZ-2500`、`V7`、`V15`），**其余 23 题名次完全不变**。这是本次改动的核心验收点：**有效提权 + 零退化**。

> 这两次运行还提供了一个额外的可信度旁证：`vector` 与 `keyword` 两列在两份结果里**逐题完全一致**（58 个格子）。这两路完全不受重排开关影响，所以它们一致，说明两次评估跑在同一份索引上、且索引在两次运行期间没有变动。

## 五、结论解读

### 5.1 单路检索必然在某一组上掉分

- 纯向量在含编号的查询上 Hit@1 只有 **70.0%**。这正是向量的结构性弱点：模型训练时几乎见不到 `ERROR 1451`、`XZ-2500`、`V8__add_source_retriever` 这类字符串，它们的向量方向会退化成「数据库报错」这种泛化语义，导致含编号的片段和不含编号的片段混在一起、无法区分。
- 纯关键词补上了这一块（**85.0%**），但代价是在纯语义提问上掉到 **87.5%**——低于纯向量的 **100.0%**。因为它只认字面重合，用户换个说法就问不到了。

**两者是互补的，不是竞争关系**。这正是混合检索存在的理由。

### 5.2 混合检索拿到了两者的上界

混合检索在两组上的 Hit@1 都是 **100.0%**，等于同时拿到了向量在语义上的优势和关键词在字面上的优势，而没有继承任何一方的短板。

### 5.3 融合与重排解决的是两个不同的问题

- **RRF 融合**解决「两路怎么合」。只用排名不用分数，天然免疫量纲差异（向量相似度有固定上界，BM25 分数无上界），无需调参。
- **重排**解决「合完之后哪几条真的最相关」。本项目在未配置外部 Cross-Encoder 时，用「标识符命中」做加法提权。

融合之后 Hit@1 是 82.1%，重排把它推到 100.0% —— 说明融合阶段已经解决了大部分问题，重排是**最后一段精修**，而不是主力。

## 六、一次真实的排错记录

这一节是本报告最有价值的部分。改动方向看起来完全合理，实测却是退化的。

### 6.1 现象

最初版本的重排器用「IDF 加权词覆盖率」对候选整体重新打分排序。实测结果：

```
hybrid Hit@1  89.3%   ← 低于纯关键词的 92.9%
```

**一个「更聪明」的重排器，反而让结果比不加它更差。**

### 6.2 定位

逐段拆解打分链路（vector → keyword → RRF-only → RRF+rerank），锁定了具体失效的那道题：

查询 `V8 迁移脚本做了什么改动`，正确答案被从 **#1 挤到了 #3**。

进一步打印分词结果，找到两个根因：

**根因 A：标识符分词不匹配。** 查询里的 `V8` 被切成 token `v8`，而文档里的 `V8__add_source_retriever` 只产出一个整体 token。两边**永远匹配不上**——而这个 `v8` 恰恰是整条查询里最有区分度的词。BM25 和重排的词覆盖率都给它记了零分。

> 修复：分词时对含分隔符的标识符**同时产出整体 token 和分段 token**。整体 token 保留，所以精确匹配长标识符的能力不受影响。

**根因 B：噪声 bigram 污染重排。** 查询「V8 迁移脚本做了什么改动」在 bigram 切分下会产出 `了什`、`么改` 这类**跨词边界的偶然组合**，而另一篇讲索引的文档标题恰好是「索引做了什么」——靠噪声匹配拿到了虚高的覆盖率，被提到第一位。

> 修复：重排**只采信「标识符类」词元**（含字母数字的编号、型号、版本号、类名）。中文的普通词元一律不参与重排打分。

### 6.3 修复：从「全局重排」改成「加法提权」

这是本次最重要的设计决策：

```
最终分 = 原融合分 + 标识符命中加成 + 整串命中加成
```

关键在于**只做加法、不做归零重排**：

- 查询里**没有**标识符时，加成恒为 0，排序**完全等于**融合结果 —— 所以不可能退化；
- 查询里**有**标识符（错误码、型号、版本号）时，命中它的片段被抬上来 —— 这正是关键词召回存在的意义。

**一条工程原则：一个能推翻融合结果的弱重排器，比没有重排更糟。**

本地重排器不是 Cross-Encoder，它的判别力远不如真模型。让它拥有「把 #1 挤到 #3」的权限，就是在用弱信号覆盖强信号。改成加法提权之后，它的权限被严格限制成「在已有排序上做有限的上浮」，最坏情况只是不生效，而不会破坏已有结果。

### 6.4 一个顺带发现的展示缺陷

提权实现后，引用面板上出现了多条「相关度 1.00」并列的情况——因为展示分数被 `min(final, 1.0)` 截断，**凡是命中标识符的片段全部饱和到 1.00**，用户完全分不出主次。

> 修复：展示分数按本轮最高分**重新缩放**（`final / max`），而不是直接截断。既保持「排序与分数同序」，又让名次之间有可读的落差。

## 七、评估集自身的两次修正

评估集的缺陷会直接变成错误的工程结论，所以它本身也要被审查。

### 7.1 第一次修正：文档级 → chunk 级

第一版按「命中了哪篇文档」判分，而每篇文档只有 1 个 chunk。结果三种模式全部 100%，测不出任何差异。改成 chunk 级 + 长目录型语料后，差异才显现出来（纯向量 Hit@1 从 100% 掉到 60.7%）。

### 7.2 第二次修正：只认编号 → 编号 + 答案文本

第二版只要求编号出现。实测发现两类虚高（见 3.3 节）。修正后纯关键词的 Hit@1 从 92.9% 降到 **89.3%**，纯向量从 60.7% 微降到 60.7%（MRR 78.6% 不变）——**指标下降的不是系统，是原先虚高的部分被挤掉了**。

同时发现 `两路检索结果是怎么合并的` 一题在三种模式下**都排不到第一**。逐条打印结果后确认：这不是检索缺陷，而是**题目本身有歧义**——`retrieval-overview.md` 写「只看名次不看分数，把两路的名次做倒数后相加」，`hybrid-retrieval.md` 写「只使用名次不使用分数」，**两处都是正确答案**。把判分钉在其中一篇上，会让检索器因为「挑中了另一个正确片段」而被判错。

> 修复：引入 `answer_any`（任一备选成立即算命中），把题目歧义和检索缺陷区分开。

> **口径提示**：本节（以及第六节）里的数字都来自**切片升级之前**的那一版评估——那时语料被切成 16 个 chunk。切片改成结构感知之后，同一套 28 题重新跑出来的数字见第十一节。两节描述的是同一套评估体系在不同切片策略下的表现，叙述逻辑不变，数值不要混用。

## 八、局限

**这一节必须读。** 上面的 100% 是在以下条件下取得的，不能外推：

1. **评估集规模小**：28 题、44 个 chunk。这个量级下单个题目的得失就是 3.6 个百分点，统计意义有限。
2. **评估集是自己编写的**，语料的用词风格、难度分布都由我决定，存在**无意识的自我偏袒**风险。真实用户提问的措辞多样性远高于此。
3. **语料是自造的合成文档**，不是真实业务文档。真实文档有图片、超长段落、合并单元格等更复杂形态，切片质量会明显更差。本项目新支持的 xlsx / pptx / html 格式**没有进入这套评估集**，它们的切片质量目前只有单元测试覆盖，没有量化指标。
4. **判分依据由字符串匹配决定**，无法覆盖「语义上等价但用词完全不同」的情形。
5. **100% 不等于完美**。它只说明「在这 28 道题上，正确片段都被排到了第一位」。

### 后续值得做的事

- 把评估集扩到 100 题以上，并引入**他人编写**的题目，消除自我偏袒；
- 接入真实的 bge-reranker / Cohere rerank，在同一个评估集上比较「本地提权」与「真 Cross-Encoder」的差距；
- 增加**切分质量**指标：统计「答案被切断」的比例（`1836` 那种情况），指导切片参数调优。**结构感知切片在很大程度上消除了这个问题**（条目不再被从中间切断），但目前只是「肉眼验证 + 单元测试」，还没有把它变成一个随参数自动计算的指标——`chunk_size` 一改，就需要重新验证；
- 为 xlsx / pptx / html 建一套小规模评估语料，把「新支持了格式」变成「新格式的切片质量也被量化过」；
- 记录每次参数调整后的指标，形成回归基线。

## 九、复现方式

```bash
# 1. 把 docs/rag-eval/corpus/ 下的 10 篇文档上传到同一个知识库，记下知识库 ID
# 2. 在 ai-service 容器内运行：
AI_SERVICE_EVAL_KB_ID=<知识库ID> \
AI_SERVICE_EVAL_QUESTIONS=/docs/rag-eval/questions.json \
python scripts/evaluate_retrieval.py
```

脚本会输出逐题明细、总体指标、分组指标，以及 hybrid 未排第一的题目清单（用于区分「召回失败」和「排序失败」）。

### 9.1 评估之前先做索引自检（第 11.6 节的教训已固化进脚本）

**指标只有在索引可信的前提下才有意义**，所以评估前必须先过这一关：

```bash
# 只检查，不动数据 —— 建议每次评估前都跑
python scripts/verify_index.py --knowledge-base-id <知识库ID> \
    --questions /docs/rag-eval/questions.json

# 如果刚改过切片策略，需要先按新策略重建索引再检查
python scripts/verify_index.py --knowledge-base-id <知识库ID> --reindex \
    --questions /docs/rag-eval/questions.json
```

自检给出两条**互相独立**的证据：

| 证据 | 证明什么 | 不过关意味着 |
| --- | --- | --- |
| 多次（默认 3 次）chunk 总数与逐文档分布完全一致 | 索引「没在变」 | 有并发写者同时在改索引 |
| 每道题的判分串与库里全部 chunk 字面匹配 0 缺失 | 索引「答案真的在里面」 | 语料缺失或入库失败 |

两条都通过才输出「索引可信：是」（退出码 0），否则退出码非 0，便于接进 CI。关键点是：**这两条证据都不经过向量和 BM25**，所以它们和检索器完全独立 —— 任何一条不过关，就说明问题不在检索质量上。

`--reindex` 走的是**同进程同步调用**（`replace_existing=True` 的实现是「先删旧 chunk 再写入」，HTTP 提交后台任务再轮询会读到删除与写入之间的中间态），并会先清掉表里非 `COMPLETED` 的残留任务 —— 服务的任务恢复是每几秒轮询一次的循环，不清掉的话它会在观测期间插进来改索引。

### 9.2 其余实验

对照实验（关掉重排，即仅 RRF 融合）：

```bash
AI_SERVICE_RERANK_ENABLED=false \
AI_SERVICE_EVAL_KB_ID=<知识库ID> \
python scripts/evaluate_retrieval.py
```

单元测试（判分逻辑本身也有测试保护 —— 它决定所有指标是否可信）：

```bash
cd ai-service && python -m pytest tests -q
```

判分口径（`answer_span` / `answer_any` 的解析、命中判定、指标汇总）只有一份实现，放在 `app/eval_judging.py`，由**评估脚本与自检脚本共用**。如果两边各写一份，只要有一边改了口径，就会出现「评估说 MISS、自检说可答」这种自相矛盾的结论 —— 而自检的全部意义正是给评估提供独立但**同口径**的证据。

## 十、面试可以怎么讲

这套评估体系本身就是一份可讲的材料，因为它包含了一个**真实的技术判断失误与纠正过程**：

> 我们做混合检索时，一开始按常识加了一个基于词覆盖率的重排器，方向看起来完全合理，但实测 Hit@1 反而从 92.9% 掉到 89.3%（切片升级前的口径）。我逐段拆解打分链路把问题定位到两个点上：一是标识符分词不匹配（查询写 `V8`、文档写 `V8__add_source_retriever`，两边永远匹配不上）；二是中文 bigram 产生的跨词噪声（`了什`、`么改`）污染了覆盖率打分，把无关片段提到了第一位。
>
> 修复时我做了个判断：**一个能推翻融合结果的弱重排器，比没有重排更糟**。本地重排器不是 Cross-Encoder，判别力不够，不该拥有推翻融合结果的权限。所以我把它从「全局重排」改成「加法提权」——查询里没有标识符时加成恒为 0，排序完全等于融合结果，绝不可能退化；有标识符时命中它的片段被抬上来。改完 Hit@1 回到 100%，而且只在它该起作用的 5 道题上改变了名次，其余 23 题零退化。
>
> 过程中我还修了两次评估集本身：一开始按文档判分，因为每篇文档只有一块，所有方案都是 100%，根本测不出差异；改成 chunk 级判分后又发现只认编号会虚高，因为一篇只罗列型号的目录片段也含 `2500`。评估集有缺陷会直接变成错误的工程结论，所以它本身也得被审查。

这段之所以值得讲，不在于「我用了 RRF」，而在于**有指标、能定位、能承认自己最初做错了，并且给出了明确的设计约束来防止同类错误再发生**。

第二个可讲的点在第十一节：**切片改完之后的第一次评估，指标是不可信的**。同一份代码、同一份评估集，连续跑出三组不同的数字。我没有直接去解读「指标怎么变了」，而是先花时间证明索引本身可信，最后发现是评估跑在了正在被并发写入的索引上。这件事的说服力在于：**先怀疑测量，再相信结论。**

## 十一、切片策略升级（阶段三）

### 11.1 问题：旧切片把文档结构切没了

旧实现的全部逻辑就两行：

```python
text = " ".join(text.split())   # 把换行、空行一起压平
chunks = [text[i:i + size] for i in range(0, len(text), size - overlap)]   # 按固定字符等距切
```

第一行就把**段落边界**毁掉了——`split()` 会把换行当普通空白扔掉，文档从此变成一长串无结构的字符。

第二行看起来是「等距切，稍微重叠一点」，实际后果是**它必然把语义单元从中间切断**：

- 50 个错误码的目录，某个条目会被切成「前一半」和「后一半」，两片都不完整；
- 表格行会被从列中间切断；
- 一段讲「覆盖索引」的话可能前半段落在上一片、后半段落在下一片。

上一版评估集里 `1836` 同时出现在**完整条目**和**截断残句**两个 chunk 里（见 3.3 节），就是这个问题的直接产物。

而且 `overlap = 120` 本质上是**碰运气**：它靠「让答案至少完整地出现在某一片里」来兜底。重叠越大越不容易切坏，但重复内容也越多、检索时越容易被相似片段干扰。

### 11.2 做法：抽取阶段带出结构，切片只在结构边界上

核心思路是**把「文档 → 纯文本」改成「文档 → 结构化块列表」**，每个块自带它所属的标题链：

```python
@dataclass(frozen=True)
class DocumentBlock:
    text: str
    kind: str = "text"                        # text / row / page
    heading_path: tuple[str, ...] = ()        # 例如 ("退款政策", "审批流程")
```

切片器只做一件事：**在块边界上打包，标题变化是硬边界**；只有当单个块自己就超过 `chunk_size` 时，才退化成字符滑窗（此时无边界可用）。

块边界来自各格式自身的结构，而不是猜出来的：

| 格式 | 块边界 | 附带的结构信息 |
| --- | --- | --- |
| Markdown | ATX 标题（`#`~`######`） | 标题链（层级回退：同级替换、下级下钻） |
| PDF | 页 | `第 N 页` |
| DOCX | 段落 | `heading N` / `标题 N` 样式推出层级 |
| CSV / XLSX | 行 | 首行作表头，之后每行成块 |
| PPTX | 页 | 每页首段作页面标题 |
| HTML | 标题 / 段落 / 表格行 | `h1`~`h6` 标题链，`script`/`style` 跳过 |

### 11.3 关键设计：标题前缀（上下文注入）

这是**投入产出比最高的一处改动**。每个 chunk 在入库前会被加上它所属的标题链：

```
索引基础概念 > 覆盖索引
如果索引里已经包含了查询需要的全部列，数据库就不必回到主表取数据，
这种情形称为覆盖索引，能显著减少随机读取。
```

对比一下两种思路：

| 思路 | 机制 | 代价 | 可靠性 |
| --- | --- | --- | --- |
| 调大 `overlap` | 让答案至少完整地出现在某一片里 | 重复内容变多，相似片段互相干扰 | 碰运气 |
| 加标题前缀 | 让每个片段自带它的上下文位置 | 每片多几十个字符 | 确定性 |

而且标题前缀对**向量检索**的作用是结构性的：`覆盖索引 > ... 不必回到主表取数据` 这样的文本，其向量会明确落在「索引优化」这个语义区域；而旧实现里那几百字可能同时混着索引、锁、事务几个话题的碎片，向量方向被平均成一段没有主题的模糊区域。

### 11.4 表格的处理：按行成块，每块重复表头

表格最容易切坏。若把整张表当成一整段文本，行列会错位；若按字符滑窗切，表头会和数据分家。采用的办法是**一行一个块，且每块都带上表头**：

```
型号: XZ-2500 | 默认限流: 每秒两百次
```

这样每一行都是一个**语义完整、自解释**的片段——即使被单独召回，也能看懂它在说什么，并且**仍然含有判分所需的型号和数值**。这也顺带解决了「目录片段含型号但没有答案」那类误判的根源。

### 11.5 效果：16 chunk → 44 chunk，指标全面变化

同一套 28 题、同一套判分口径，只换切片策略：

| 配置 | 指标 | 旧切片（16 chunk） | 新切片（44 chunk） | 变化 |
| --- | --- | ---: | ---: | ---: |
| 纯向量 | MRR | 78.6% | 87.6% | **+9.0** |
| 纯向量 | Hit@1 | 60.7% | 78.6% | **+17.9** |
| 纯关键词 | MRR | 94.0% | 91.7% | −2.3 |
| 纯关键词 | Hit@1 | 89.3% | 85.7% | −3.6 |
| 混合检索 | Hit@1 | 100.0% | 100.0% | — |

三点解读：

1. **纯向量提升最大（Hit@1 +17.9pp）**，而且它的纯语义分组直接从 87.5% 升到 **100.0%**。这印证了 11.3 节的判断：标题前缀 + 完整的语义单元，让向量终于拿到了主题信息。旧实现下向量在语义题上也不稳，说明「无主题的长窗口」对向量同样有害。
2. **纯关键词小幅回落 3.6pp**，恰好等于 1 道题（28 题里 1 题 = 3.6pp）。原因是切片变细后候选片段变密、相似片段之间的 BM25 分差缩小。在 28 题的规模下这属于噪声范围，不宜据此下结论——但它是一个**需要留意的方向**：切片粒度会同时影响两路召回的相对强弱。
3. **混合检索保持 100% 且零退化**，说明融合与提权机制对切片变化是鲁棒的。这也正是混合检索的价值所在：任一路单独波动，最终排序不受影响。

### 11.6 方法论教训：先证明索引可信，再解读指标

这一小节记录的是本次真正的坑，它和检索本身无关，但差点把结论带偏。

**现象**：切片改完重跑评估，同一份代码、同一份评估集，连续跑出了三组互相矛盾的数字：

| 轮次 | Recall@5（vector/keyword/hybrid） | MRR | Hit@1 |
| --- | --- | --- | --- |
| 1 | 100 / 100 / 100 | 85.2 / 90.8 / 97.6 | 75.0 / 85.7 / 96.4 |
| 2 | 96.4 / 100 / 96.4 | 84.0 / 91.7 / 96.4 | 75.0 / 85.7 / 96.4 |
| 3（最终） | 100 / 100 / 100 | 87.6 / 91.7 / 100.0 | 78.6 / 85.7 / 100.0 |

同一道题（`覆盖索引为什么能变快`）在 vector 与 hybrid 两路都出现过 MISS，而它在 keyword 里排 #1 —— 这个组合**看起来非常像「向量索引里那条数据丢了」**。最初的怀疑是 Milvus 主键复用竞态：chunk id 由 `sha256(f"{object_key}:{index}")` 生成，重新切片后下标 0 会复用同一个主键，「按主键删除 + 插入同一主键」是 Milvus 的经典问题。

**排查过程**（关键是每一步都尽量用独立证据，不靠推断）：

1. **直接查库**：把该知识库全部 chunk 拉出来，确认含「不必回到主表取数据」的片段**确实存在**，只有 1 条，长度 70。
2. **直接向量检索**：绕开混合检索，单独调 `vector_search` 取全部候选 —— 该片段排**第 1 位**，score = 0.7475。
   → 到这一步已经可以排除「向量索引丢数据」和「主键复用导致实体被吞」。**假设被证伪了。**
3. **反向验证**：把 28 道题的判分串与库里全部 chunk 做**纯字面匹配**（完全不经过向量/BM25）—— 结果 28 题**全部命中**。
   → 说明语料和入库都是完好的，问题只能在「写入过程中的某一时刻」。
4. **看进程**：列出容器内进程，发现**同时有两个 `reindex_sync.py` 在跑**。

**结论**：故障源不在 Milvus，也不在检索器，而在**索引在被并发写入的同时被读取**。那次排错中我用 `docker exec` 启动的重索引脚本被工具超时中断，但**容器内的进程并没有随之退出**，于是两个循环同时对同一批文档执行「先删旧 chunk → 再写入新 chunk」，互相覆盖。表现出来就是：

- 同一篇文档的切片数在两轮统计间从 5 变成 0（正处在「已删、未写」的窗口期）；
- 某篇文档**整篇从对象列表里消失**，导致重索引脚本报出「9 篇文档」（它从 Milvus 取 object_key 列表，而那篇此刻恰好是空的）；
- 同一道题时好时坏。

**由此确立了两条索引可信度的验收标准**，此后每次评估前都必须先过这两关：

| 证据 | 证明什么 | 做法 |
| --- | --- | --- |
| **多次计数一致** | 索引「没在变」 | 连测 3 次 chunk 总数与逐文档分布，间隔若干秒，必须完全一致 |
| **答案字面可命中** | 索引「答案真的在里面」 | 每道题的判分串与库里全部 chunk 做纯字面匹配，必须 0 缺失 |

第二条比第一条更强：计数一致只能说明「稳定」，而字面命中才说明「内容对」。两者都通过，指标才有解读价值。

**一句话教训**：**指标异常时，先怀疑测量，再怀疑系统。** 如果当时直接去改 `index_chunks` 的主键生成逻辑（那是个看起来完全合理的改动方向），就会白改一版代码，而且因为并发窗口是随机的，改完还可能「看起来好了」。

### 11.7 面试可以怎么讲

> 我们的切片原来是「把整篇文档压成一行纯文本、再按 800 字符等距切」。这个做法有两个结构性缺陷：一是压平换行时把段落边界丢了，二是等距切必然把语义单元从中间切断——50 个错误码的目录里，某个条目会被切成不相连的两半，两片都不完整。
>
> 我把它改成了结构感知切片：**先做结构化抽取**，把文档变成一组带标题链的块（`heading_path`），**再只在块边界上打包**，标题变化是硬边界，只有单个块自己超长时才退化成字符滑窗。每种格式的边界来自它自己的结构——Markdown 是 `#` 标题，Excel 是一行一条记录且每块重复表头，PPT 是一页一块，HTML 是标题加表格行。
>
> 最关键的一处改动是**给每个 chunk 加上它所属的标题链前缀**，比如「索引基础概念 > 覆盖索引」。原来的兜底手段是调大 overlap，本质上是碰运气让答案别正好落在切口上；加前缀是确定性地让每个片段自带上下文。实测纯向量的 Hit@1 从 60.7% 提到 78.6%，语义题从 87.5% 提到 100%，而混合检索保持满分零退化。代价几乎为零——每片多几十个字符。
>
> 这个过程里我踩了一个更值得讲的坑：改完第一次跑评估，同一份代码连续跑出三组不同的数字，有一道题在向量和混合两路都 MISS 但关键词排第一，非常像向量索引丢数据。我一开始怀疑是 Milvus 主键复用竞态。但我没有直接去改代码，而是先做了三件事验证：直接查库确认那条数据在；绕开混合检索单独跑向量检索，发现它排第一；把 28 道题的判分串跟库里所有 chunk 做纯字面匹配，全部命中。**假设被证伪了。** 最后查到真实原因是容器里同时跑着两个重索引进程，一个删、一个写，我读到的一直是中间态。
>
> 所以我现在形成一个习惯：**指标异常时先怀疑测量，再怀疑系统。** 并且给评估加了两条前置验收：索引连测三次计数必须一致，每道题的判分串必须能在库里字面命中——两条都过了，指标才值得解读。

## 十二、查询改写（Multi-Query）与新格式语料（阶段六 B 组）

> 本节回答两个问题：**查询改写到底值不值得开**，以及**新格式文档进了索引之后能不能被检索到**。
> 结论先说：新格式那条链路**已被 13/13 全召回证明打通**；查询改写**默认不开**，理由见 12.7。

### 12.1 查询改写是什么，为什么要做

混合检索已经把「意思」（向量）和「字面」（BM25）覆盖了，但两者**都只在用户那一种表述上工作**。用户问「数据库一查就卡，我怎么找出那些拖后腿的语句」，语料里写的是「慢查询定位」——词面不重合、语义距离也不够近，两路一起失效。

多查询（Multi-Query）的做法：先用模型把问题改写成几种不同说法，**各自召回一遍**，再把几份排名用 RRF 融合。命中任意一种说法的片段都能进来；而「被多种说法同时召回」的片段自然被抬到前面。

### 12.2 第一次测量：在主评估集上，它 0 改善

在既有的 28 题评估集上跑四档（新增 `rewrite` = 混合检索 + 改写）：

| 模式 | Recall@5 | MRR | Hit@1 |
| --- | ---: | ---: | ---: |
| vector | 100.0% | 87.6% | 78.6% |
| keyword | 100.0% | 91.7% | 85.7% |
| hybrid | 100.0% | 100.0% | 100.0% |
| rewrite | 100.0% | 100.0% | 100.0% |

**逐题对比：变好 0 题 / 变差 0 题 / 不变 28 题。**

这不是「改写没用」，而是**这批题根本测不出它有用**：hybrid 在这 28 题上已经是 100% Hit@1，天花板到了，任何改动都不可能让它更好。

### 12.3 由此得到的一条方法论：**一个功能，不能在一个「它不可能失败」的题集上被验证**

回头看这批题为什么这么容易：**它们的措辞就是从语料里抄的**。出题时为了判分清楚，我把语料原句（「慢查询日志」「覆盖索引」「最左前缀」）直接搬进了问题里 —— 于是 BM25 只要字面匹配就能命中，题目退化成了「考检索器会不会做字符串查找」。

而真实用户**不知道语料的术语**。他只会说「查出那些拖后腿的语句」。措辞的这道鸿沟，恰恰是查询改写要解决的问题 —— 但原评估集里根本没有这种题。

所以补了一套 **`questions-paraphrase.json`**，语料不变、判分口径不变、库也不变（同一个 KB），**只改提问的措辞**。设计原则只有一条：**每道题都不使用语料中的术语**（说「回原本那张表」而不说「回表/主表」，说「单独查后一个字段」而不说「最左前缀」）。

### 12.4 顺手补的一个前置工具：离线核对判分串

写这套题时最怕的不是检索不行，而是**判分串自己写错**：语料写「不必回到主表取数据」，题目手写成「不用回主表」——一个字之差，评估永远是 MISS，然后你会去排查检索器、BM25 参数、向量维度，**方向从第一步就错了**。

`verify_index.py` 能查这件事，但它要连 Milvus（查的是「已入库的 chunk」），**写题的时候还用不上**。所以加了 `scripts/verify_question_spans.py`：不连库、不连网，直接用**生产同一套切片参数**把语料切一遍，再复用**评估本身那套匹配函数**核对每条判分串，并顺带核对 `expect_doc`。

```
$ python scripts/verify_question_spans.py --questions ../docs/rag-eval/questions-paraphrase.json
语料：10 篇 → 44 个 chunk（chunk_size=800, overlap=120）
  [OK  ] 数据库一查就卡，我怎么找出那些拖后腿的语句
         命中 1 片，落在：db-tuning.md
  ...
全部题目的判分串都能在语料里字面命中。
```

顺带一个可信度旁证：它离线切出的 **44 个 chunk** 与线上索引里的数量一致 —— 说明离线核对与生产入库用的是同一套切片策略，不是两套近似实现。

### 12.5 口语化题集的结果（**跑了两次**）

| 模式 | Recall@5 | MRR | Hit@1 | 说明 |
| --- | ---: | ---: | ---: | --- |
| vector | 91.7% | 61.8% | 41.7% | 两次运行**逐题完全一致** |
| keyword | 83.3% | 55.8% | 41.7% | 两次运行**逐题完全一致** |
| hybrid | 91.7% | 63.2% | 41.7% | 两次运行**逐题完全一致** |
| rewrite（第 1 次） | **100.0%** | 75.7% | **58.3%** | 变好 5 / 变差 1 / 不变 6 |
| rewrite（第 2 次） | **100.0%** | 62.5% | 33.3% | 变好 3 / 变差 2 / 不变 7 |

**为什么要跑两次**：改写由模型按温度 0.8 生成，**不可复现**。只跑一次就下结论，等于把一次抽样的运气当成结论。这里特意跑两次、并把每道题实际用到的改写存了档（`AI_SERVICE_EVAL_REWRITES_OUT`），就是为了让「数字是怎么来的」可回看。

两次结果给出一个**分得很清楚**的结论：

| 信号 | 两次是否一致 | 可信度 |
| --- | --- | --- |
| **Recall@5：91.7% → 100%**（原本完全没召回的那道题被救回来） | 两次都复现 | ✅ 可信 |
| MRR / Hit@1 的提升 | 一次 58.3%、一次 33.3%（baseline 恒为 41.7%） | ⚠️ 不可信 |

- 前 3 列在两次运行里**逐题完全一致**，说明索引没变、非 LLM 的检索路径是确定性的 —— 变动的只可能是改写本身。
- **改写稳定改善的是「有没有捞到」**（Recall），因为多几种说法等于多几次召回机会。
- **改写不能稳定改善「排得够不够前」**（MRR/Hit@1）：RRF 把「原问题」和「几条改写」放在同等地位融合，改写质量一波动，名次就跟着动。第 2 次里有 2 道题从 #1 掉到 #2。

### 12.6 附带发现：在极小语料上，融合反而会拖后腿

给新格式语料单独建库（4 篇 / 10 个 chunk）跑 13 题：

| 模式 | Recall@5 | MRR | Hit@1 |
| --- | ---: | ---: | ---: |
| vector | 100.0% | 100.0% | 100.0% |
| keyword | 100.0% | 100.0% | 100.0% |
| hybrid | 100.0% | 96.2% | **92.3%** |
| rewrite | 100.0% | 96.2% | 92.3% |

**两路单飞都满分，融合之后反而丢了一题的第一名**（「V16 版本的灰度批次代号是什么」被排到 #2）。

原因不神秘：融合的价值来自「两路互补」，而这里语料只有 10 片、内容彼此高度不同，两路本来就都对，融合只是在**给本来就正确的排序引入额外扰动**。这跟第六节「弱重排器比没有重排更糟」是同一类现象 —— **一个在信息不足时介入的合并步骤，可能把原本正确的答案挤下去。**

> 这也提醒：**评估结论必须带上语料规模**。同样一份 hybrid 策略，在 44 个 chunk 上是满分、在 10 个 chunk 上会丢分。

### 12.7 新格式语料纳入评估集（13 题，全部召回）

阶段三把解析从 markdown 扩到了 Excel / PPT / HTML / CSV / DOCX / PDF，但评估集一直只有 10 篇 `.md` —— 「新格式能不能进索引、进去后能不能被检索到」从来没被量化验证过。

这次补齐：
- 语料由 `docs/rag-eval/build_new_format_corpus.py` 生成（**标准库手写 OOXML**，与 ai-service 的解析器保持同一依赖水平；生成后可 `--verify` 用真实解析器 + 真实切片器回读自检）。
- 四份语料各锁一个解析要点：xlsx 的**第二个工作表**、pptx 的**第 2/3 页**、csv 的**表头与数据同片**、html 的**第三个 `<h2>` 小节**，外加一条「`<script>` 内容不得进索引」的反向断言。
- 语料构建走**真实 HTTP 链路**（`scripts/build_eval_knowledge_bases.py`：注册评估账号 → 建库 → 上传 → 轮询解析完成），不是直接塞 Milvus。

**结果：13 题全部被四档模式召回（Recall@5 = 100%），表格类 7 题与网页类 3 题 Hit@1 全为 100%。** 这直接证明「xlsx/pptx/csv/html → 解析 → 结构化切片 → 入库 → 检索」整条链路是通的。

> 一个设计取舍：新格式语料**单独建库**而不是塞进主评估库。因为主库已有 44 个 chunk，任何 MISS 都要先分辨是「解析没进去」还是「被别的文档挤掉了」；单独建库后库里只有这 10 片，MISS 只可能有一个病因。

### 12.8 结论：默认**不开启**，但功能保留

证据摆在一起是这样：

| 维度 | 结论 |
| --- | --- |
| 能不能提升召回 | ✅ 能，Recall@5 91.7% → 100%，两次复现 |
| 能不能稳定提升排序 | ❌ 不能，Hit@1 一次比 baseline 好、一次比 it 差 |
| 在措辞取自语料的题上 | 无影响（0 变好 / 0 变差），也无害 |
| 代价 | 每次提问多一次模型调用（延迟 + token） |

**所以 `query_rewrite_enabled` 默认为 `false`**（`app/settings.py`）。理由不是「没做完」，而是：

> **一个稳定的收益（召回）和一个不稳定的收益（排序）绑在一起，还附带每次提问的一次额外模型调用 —— 这个组合不足以支撑默认开启。**
> 要把它变成默认值，需要的是**更大的口语化评估集 + 多次运行取平均**，而不是在 12 道题上给融合权重调参。后者正是第六节已经踩过的坑：**拿一个小样本去拟合一个弱机制，比不做更糟。**

开启方式：`AI_SERVICE_QUERY_REWRITE_ENABLED=true`（Agent 的工具检索路径不受它影响，见下）。

### 12.9 一个刻意的范围限制：Agent 路径不做改写

`agent_tools.knowledge_search` 显式传 `rewrite=False`，这是有意的：

- Agent 的检索 query 是**模型自己写的**，而且它会**跨轮换措辞重试** —— 它本身已经在做「多查询」了；
- 在工具内部再套一层改写，等于**每一轮工具调用都多打一次模型**，而收益与模型自己换措辞高度重叠。

有一条单测专门钉住这个参数（`test_knowledge_search_disables_query_rewrite`），别人把它去掉会立刻变红。

### 12.10 面试可以怎么讲

> 我给检索加了个查询改写（Multi-Query）：先用模型把用户问题改写成几种说法，各自召回后用 RRF 融合。
>
> 但真正值得讲的不是这个功能，而是**我怎么确认它到底有没有用**。我拿它跑了现有的 28 题评估集，结果是**变好 0 题、变差 0 题** —— 完全没变化。这时候很容易得出「改写没用」的结论，但我去看了一眼为什么：**那批题的措辞是从语料里抄的**（问「慢查询日志」而不问「怎么找出拖后腿的语句」），所以混合检索已经是 100% Hit@1，天花板到了，**任何改动都不可能让它更好**。**一个功能，在它不可能失败的题集上是测不出来的。**
>
> 于是我另做了一套题，语料、判分口径、库都不变，**只把提问改成真实用户的口语**，并且刻意不用语料里的任何术语。跑出来 hybrid 的 Hit@1 只有 41.7%，改写 58.3%。但改写是模型按温度 0.8 生成的、不可复现，所以我**又跑了一遍**：这次 Recall@5 还是 100%（比 hybrid 的 91.7% 好，两次都复现），可 Hit@1 掉到 33.3%，比 baseline 还差。前三个模式两轮**逐题完全一致**，说明变动只来自改写。
>
> 结论我定的是：**默认不开**。它稳定改善的是「有没有捞到」，不能稳定改善「排得够不够前」，还要每次提问多打一次模型 —— 这个组合不够格当默认值。要开启得先有一个更大的口语化评估集、多次运行取平均，而不是在 12 道题上给融合权重调参；那正是我之前踩过的坑：**拿小样本拟合一个弱机制，比不做更糟。**
>
> 另外顺手补了两件事：一是把 xlsx/pptx/csv/html 四种新格式的语料纳入评估集并单独建库，13 题全部召回，证明「解析 → 切片 → 入库 → 检索」整条链路是通的；二是发现**在只有 10 个 chunk 的小语料上，混合检索反而不如任一单路**（丢了一题的第一名）—— 融合的价值来自两路互补，语料小的时候它只是在给正确的排序引入扰动。所以**评估结论必须带上语料规模**。

## 十三、Cross-Encoder 精排（阶段八）：一次「先拿到收益、再抓到回归、最后用加法组合收口」的完整闭环

### 动机：换说法题集暴露的排序空间

第十二节的换说法题集上，hybrid 的 **Hit@1 只有 41.7%，而 Recall@5 有 91.7%**——正确片段几乎都被捞进 top-5 了，只是排位不对。这正是 Cross-Encoder 精排的定义域：双编码器（向量 / BM25）从不让 query 与 doc 交互，换一种说法就分不出高下；精排阶段逐对比较，理论上恰好补这一段。

provider 选了百炼 gte-rerank-v2（DashScope 原生端点）：与 embedding 同一把密钥，不新增供应商与部署件；实现里它必须能退回本地保守提权（fail-open——重排是增强项，不该拖垮检索主链路）。

### 第一轮实测：收益与回归同时出现

| 指标 | hybrid（基线） | rerank（纯 CE 排序） |
| --- | ---: | ---: |
| 换说法题集 Hit@1 | 41.7% | **66.7%**（+25pp） |
| 换说法题集 MRR | 63.2% | **72.8%**（+9.6pp） |
| 换说法题集 Recall@5 | 91.7% | 91.7% |
| **主评估集 Hit@1** | **100%** | **92.9%**（−7.1pp，回归） |

逐题看主集的回归：`ERROR 1215 报错怎么排查` 从 #1 掉到 #3、`两路检索结果是怎么合并的` 从 #1 掉到 #2——**含编号/型号的查询里，标识符精确命中本来已经排第一，CE 的语义分反而把它压下去了**。

### 这不是「弱重排器事故」的简单重演，而是它的下半场

第六节的教训是「一个能推翻融合结果的**弱**重排器，比没有重排更糟」——当时判据是词覆盖率这种弱信号不配拥有推翻权。这次的对象是货真价实的 Cross-Encoder（换说法集 +25pp 证明它强），但它依然**不该拿到绝对推翻权**：标识符字面命中是最强、最可靠的判别信号，任何语义模型都可能在这上面输给精确匹配。

结论升级为：**不是「强了就可以全局接管」，而是「每个信号都只该加在自己确证的范围里」**——CE 管语义排序，标识符加成管精确命中，加法组合：

```
最终分 = CE 相关性分 + 0.35 × 标识符覆盖率 + 0.15 × 整串命中
```

这个结构继承自 rerank_features 的设计：查询里没有标识符时加成恒为 0（换说法集 12 题全部如此——**所以那组 +25pp 的数字对组合版逐题原样成立**）；有标识符时精确命中被守住（回归方向由单测 `test_cross_encoder_cannot_override_exact_identifier_match` 钉死）。

### 状态与启用门槛

- 代码已合入：`app/hybrid_search.py` 的 `_apply_cross_encoder_scores`（DashScope 与 generic 两条远端路径共用组合逻辑），评估脚本新增 `rerank` 列（未配 key 时**自动摘除该列**，绝不静默退化成假数据）。
- **默认关闭**：不加 `AI_SERVICE_RERANK_*` 环境变量时行为与此前逐字节一致（本地保守提权）。compose 中已留注释接线。
- **启用门槛**：账户额度恢复后在主评估集复测组合版（一条命令：评估脚本已带 rerank 列），确认 Hit@1 回到 100% 且换说法集保持 66.7%，再打开 compose 里的三行注释。本次评估中途 DashScope 返回 `Arrearage`（欠费），主集组合版数字待补——**没有这个数字就不开默认**，规矩与查询改写一致。
